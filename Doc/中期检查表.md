## 科研工作总结

面向无人机集群协同管控系统的实现

随着无人机技术在区域安防、农业植保、应急搜救等领域的规模化应用，其作业模式正从"单机独立作业"向"中大规模集群协同作业"转变。传统单机地面站（如QGroundControl）围绕"单台无人机的点对点控制"展开，功能局限于单机电量查看、独立路径规划及点对点指令下发，既缺乏多机状态统一管理的基础能力，也无法实现集群任务协同与跨机资源调度。因此，构建一套面向集群管控需求、具备集群特定业务功能的协同管控系统，是支撑中大规模无人机协同作业的关键前提。

本文的核心研究目标是构建一个功能完善、运行可靠的无人机集群综合管控系统，系统性解决从单机管控到集群协同管控的技术跨越问题。具体而言，研究内容围绕以下三个层面展开：

第一，构建面向异构资源的统一抽象与管控模型。设计统一的无人机数据模型与适配器模式，为物理特性、通信协议各异的仿真无人机与真实无人机建立通用的状态、指令与任务描述框架。通过标准化的内部接口使上层管控功能基于统一的"逻辑无人机"模型进行交互，同时通过专用适配器完成底层协议转换与指令翻译，实现异构资源的无缝融合接入。

第二，设计与实现驱动集群智能协同的核心功能链。重点攻关"任务-资源动态匹配链"和"异常-应急协同响应链"两条关键功能链。前者基于集群全局状态感知，综合考虑任务空间拓扑、无人机动态性能等多目标因素，实现任务自动拆解与动态分配；后者在部分节点失效或环境突变时，实现集群系统的自组织与快速恢复，保障作业连续性。

第三，建立支撑功能闭环的系统架构与协同交互机制。采用微服务架构与事件驱动模型实现功能解耦与灵活扩展，通过消息队列构建异步通信骨干，确保数据流与控制流的高效传输。同时在架构中深度集成流量调度与故障自愈保障机制，确保系统在应对高并发场景时依然能提供高可用服务。

开题以来，已完成的主要工作包括：（1）完成异构通信网关（DDS网关与MAVLink网关）的设计与开发，实现仿真无人机（PX4/DDS协议）与真实无人机（MAVLink协议）的统一协议适配与标准化数据转换；（2）完成微服务架构体系搭建，将系统从单体架构重构为包含API Gateway、Business、Command、Realtime-Push、Telemetry-Ingest、Telemetry-Store、Drone-State、Common等8个独立服务模块的微服务架构，基于Kafka实现服务间异步解耦；（3）实现Commander（指挥官）→ Leader（队长）→ Pilot（飞手）三级角色权限控制体系；（4）实现从"前端操控→后端业务→通信网关→PX4飞控"的端到端指控链路闭环验证；（5）完成基于Docker Compose的容器化编排和基于kubeadm的K8s集群部署方案设计；（6）集成Prometheus + Grafana全链路监控体系与Redis Sentinel自动故障转移机制。

## 论文工作的阶段性总结（含论文工作要解决的问题、为解决问题采用的方法）

### 1. 异构通信网关的设计与实现——解决多协议异构资源统一接入问题

**要解决的问题：**

无人机集群管控面临的首要技术难题是异构通信协议的统一接入。当前主流无人机通信存在两种主要协议体系：其一是MAVLink协议，作为当前无人机地面站通信的事实标准，使用系统ID（sys_id，8位无符号整数）标识无人机，最多同时管控256架设备，且采用就近抢占式控制权模型，在集群场景下存在控制权安全性不足的问题；其二是DDS（数据分发服务）协议，基于发布-订阅模式，可突破MAVLink的数量限制，但仅支持局域网内UDP组播通信。两种协议在数据格式、控制语义、通信模式上存在根本性差异，如何在不修改上层业务逻辑的前提下实现两类无人机的统一接入与管控，是系统需要解决的基础性问题。

**采用的方法：**

本文设计并实现了基于适配器模式的双网关架构：DDS网关（dds_gateway.py / dds_rx_gateway.py / dds_tx_gateway.py，共4295行Python代码）与MAVLink网关（mavlink_gateway.py / mavlink_rx_gateway.py / mavlink_tx_gateway.py，共4503行Python代码）。

DDS网关方面：基于ROS2 rclpy客户端订阅PX4无人机发布的VehicleStatus、VehicleLocalPosition、BatteryStatus等DDS Topic，将原始ROS2消息解析并转换为系统内部统一的TelemetryMessage标准数据模型，通过Kafka消息队列发送至后端微服务。在命令下行链路上，网关监听Kafka commands.down Topic，将标准化的控制指令反向翻译为PX4可识别的VehicleCommand DDS消息并发布。为支持大规模无人机接入，实现了基于Redis的动态分片协调机制（shard_coordinator），支持多网关实例水平扩展。

MAVLink网关方面：采用与DDS网关完全对称的架构设计，通过pymavlink库监听UDP/TCP端口接收MAVLink数据包，解析HEARTBEAT、GLOBAL_POSITION_INT、SYS_STATUS等消息类型，映射为与DDS网关输出完全一致的Kafka消息格式。这一设计使得后端服务和前端界面无需任何修改即可同时管控两种协议的无人机。

在统一数据模型层面，定义了TelemetryMessage、CommandMessage、CommandAckMessage等标准化DTO（位于ucs-common模块），涵盖无人机唯一标识、GPS坐标、姿态、电量、飞行模式、武装状态等全量字段，屏蔽底层协议差异，上层所有微服务基于该统一模型进行交互。

### 2. 微服务架构体系搭建——解决单体架构无法支撑集群扩展的问题

**要解决的问题：**

原始系统采用单体Spring Boot架构（backend目录），所有业务逻辑（遥测接收、数据存储、指令下发、实时推送、用户管理等）耦合在单一进程中。这导致三个核心问题：第一，无法水平扩展，遥测数据高频写入与WebSocket实时推送争抢同一进程资源；第二，单点故障风险，任一模块异常将导致全系统不可用；第三，无法独立升级，业务迭代需全量重新部署。上述问题在集群规模增大时将成为系统性能的根本瓶颈。

**采用的方法：**

本文将系统重构为8个独立的Spring Boot微服务模块（位于ucs-platform目录，共216个Java源文件）：

（1）**ucs-api-gateway**（端口8080）：基于Spring Cloud Gateway实现统一API入口。集成JWT鉴权全局过滤器（JwtAuthGatewayFilter）和基于Resilience4j的两级API限流过滤器（RateLimitFilter，默认API 100 QPS，命令类API 10 QPS），并通过Nacos实现动态服务发现与路由。

（2）**ucs-telemetry-ingest**（端口8081）：负责从Kafka消费遥测原始数据，执行数据清洗、格式校验与Epoch时效性验证，将有效数据路由至存储与推送服务。引入EdgeStorageForwardingService支持边缘存储转发能力。

（3）**ucs-telemetry-store**（端口8082）：专注于遥测数据的持久化存储，采用批量消费模式（TelemetryBatchConsumer）写入TimescaleDB时序数据库，同时实现数据保留策略（DataRetentionService）自动清理过期数据。

（4）**ucs-realtime-push**（端口8083）：消费Kafka遥测消息，通过WebSocket/STOMP协议实时推送至前端。支持视口过滤（ViewportFilterService）——仅推送用户当前可视范围内的无人机数据，降低带宽消耗。

（5）**ucs-command**（端口8084）：负责飞行控制指令的下发与确认回执处理。实现命令幂等性（IdempotencyService），避免网络重试导致的重复指令执行。

（6）**ucs-drone-state**（端口8085）：维护无人机实时状态信息，包括设备注册（DeviceRegistrationService）、设备影子（DeviceShadowService）等IoT设备管理能力。

（7）**ucs-business**（端口8086）：承载核心业务逻辑，包括用户认证（AuthService）、团队管理（TeamService）、任务管理（TaskService）、权限控制（PermissionService）、无人机管理（DroneService）、集结点管理（RallyPointService）、地理围栏（GeofenceService）、碰撞避免（CollisionAvoidanceService）、操作日志（OperationLogService）等。实现Commander→Leader→Pilot三级角色权限模型。

（8）**ucs-common**：公共模块，定义统一数据模型（TelemetryMessage、CommandMessage等DTO）、统一错误码（ErrorCode）、统一响应封装（ApiResponse）、Kafka Topic常量、Redis Key常量、多级缓存（MultiLevelCacheService，含本地Caffeine + Redis二级缓存及Redis Pub/Sub跨实例缓存失效通知）、Resilience4j熔断配置、全局异常处理器等。

服务间通过Kafka异步通信实现解耦，关键Kafka Topic包括：telemetry.raw（原始遥测）、telemetry.validated（验证后遥测）、commands.down（下行指令）、commands.ack（指令确认）、events.drone（无人机事件）等。Kafka采用3-Broker KRaft集群部署，16个分区，3副本，支持7天消息持久化。

### 3. 多角色协同管控体系——解决集群场景下权限控制与任务协同问题

**要解决的问题：**

集群作业场景中，不同人员承担不同职责（全局监管、编队管理、单机操控），需要差异化的功能权限与操作范围。传统单机地面站不具备多角色协同机制，直接应用于集群场景将导致控制权混乱和操作安全风险。

**采用的方法：**

在后端层面，设计Commander（指挥官）→ Leader（队长）→ Pilot（飞手）三级角色控制体系。Commander负责全局舰队管理、权限分配、团队管理与操作日志审计（CommanderController）；Leader负责编队级无人机管理与任务监控（LeaderController）；Pilot执行具体的飞行控制操作（PilotController），包括ARM/DISARM、TAKEOFF、GOTO、ORBIT、HOLD、RTL等飞行指令。权限转移机制（PermissionService + transferPermission/transferPermissionToTeam API）确保控制权在层级间安全传递。

在前端层面，实现了三个独立的角色视图页面（CommanderView.tsx、LeaderView.tsx、PilotView.tsx），各视图展示对应角色权限范围内的数据与操作界面。集成2D地图（高德AMap3DPanel）与3D全息态势界面（CesiumMapPanel + HoloDashboard），支持无人机实时位置渲染、航向角同步、编队聚焦追踪、地图点击交互指令（GOTO/ORBIT/设为Home）等功能。

基于Spring Security 6.x + JWT实现接口级鉴权，通过JwtAuthenticationFilter在业务服务层校验Token，在API Gateway层通过JwtAuthGatewayFilter实现统一鉴权拦截。

### 4. 高可用与可观测性保障——解决系统单点故障与运行时不可见问题

**要解决的问题：**

集群管控系统对高可用性要求严格——任何核心服务的故障都可能导致在空无人机失去控制指令来源，造成安全事故。同时，分布式微服务架构下，各组件运行状态分散，缺乏统一可观测手段将严重阻碍故障定位与性能调优。

**采用的方法：**

高可用方面：（1）Redis采用Sentinel集群模式（3哨兵节点，配置位于redis-sentinel/），实现主从自动故障转移，Redis主节点宕机后10秒内自动选举新主节点；（2）Kafka采用KRaft模式3-Broker集群，min.insync.replicas=2确保消息可靠性；（3）所有微服务配置Docker重启策略（restart: on-failure），异常退出时自动重建；（4）集成Resilience4j熔断器（Resilience4jConfig），当下游服务不可用时自动熔断降级，防止故障级联扩散；（5）ShedLock分布式任务锁（ShedLockConfig），防止多实例部署时定时任务重复执行；（6）支持Docker多实例部署验证（docker-compose-multi-instance-microservices.yml），为K8s多副本部署做准备。

可观测性方面：（1）所有微服务集成Spring Boot Actuator，暴露/actuator/prometheus端点导出Prometheus指标；（2）部署Prometheus + Grafana + Alertmanager + Kafka Exporter + Redis Exporter全链路监控栈（docker-compose-monitoring.yml），覆盖微服务、Kafka消费Lag、Redis集群状态等多维度指标；（3）配置告警规则（alert-rules.yml），当Kafka消费Lag超阈值、微服务宕机等异常发生时自动告警。

### 5. 容器化部署与K8s集群编排——解决系统部署与弹性伸缩问题

**要解决的问题：**

微服务架构下，系统包含7个后端服务、2个网关、前端应用、4种中间件（Kafka/Redis/PostgreSQL/TimescaleDB）以及监控组件，组件众多且存在复杂的依赖关系和启动顺序约束，手动部署效率低且易出错。同时，面对无人机接入规模的动态变化，系统需具备弹性伸缩能力。

**采用的方法：**

Docker Compose层面：设计多个Compose编排文件实现分层启动——docker-compose-microservices.yml（基础设施+7个微服务）、docker-compose-kafka.yml（Kafka 3-Broker集群）、docker-compose-redis-sentinel.yml（Redis Sentinel集群）、docker-compose-monitoring.yml（监控栈）、docker-compose-gateways.yml（DDS/MAVLink网关）。通过depends_on + healthcheck确保基础设施就绪后再启动业务服务。编写一键启动脚本（scripts/startup.sh）自动化全流程。

K8s层面：编写完整的K8s部署方案（Doc/UCS_K8s集群部署完整指南.md，1371行），覆盖从OS初始化、kubeadm集群搭建、Calico CNI网络、Helm中间件部署到7个微服务Deployment + HPA自动伸缩的全流程。K8s YAML清单（k8s/目录）包含namespace.yaml、configmap.yaml、secrets.yaml、microservices-deployment.yaml、ingress.yaml等。设计Ingress-NGINX统一入口路由，并配置HPA（Horizontal Pod Autoscaler），使telemetry-ingest等流量密集型服务可根据CPU负载自动从2个Pod扩展至10个Pod。
