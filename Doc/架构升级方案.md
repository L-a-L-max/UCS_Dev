## 一、当前架构诊断

### 1.1 现有数据流

```
PX4无人机 ──DDS/ROS2(组播)──► dds_gateway.py
                               (单Python进程, 单ROS2 Node, spin_once单线程)
                                        │
                                        │ HTTP POST /api/v1/dds-gateway/telemetry
                                        │ (同步, 批量, 每秒1次)
                                        ▼
                              Spring Boot Backend (单实例, 8080端口)
                               ├── DDSGatewayController (HTTP接收)
                               ├── PartitionRoutingService (Redis→DB查分区)
                               ├── TelemetryPersistenceService (Queue→5s flush→PostgreSQL)
                               ├── WebSocketGatewayService (SimpleBroker广播STOMP)
                               └── RedisService (在线状态30s TTL)
                                        │
                                        │ STOMP WebSocket
                                        │ /topic/telemetry/partition/{name}
                                        ▼
                              React Frontend (Vite + MapLibre)
```

命令流（反向）：

```
Frontend ──HTTP──► ControlService ──HTTP──► dds_gateway.py:5050 ──DDS──► PX4
```

### 1.2 瓶颈量化分析

| 组件 | 当前能力 | 千万级需求 | 差距 |
|------|---------|-----------|------|
| **DDS Gateway** | 单进程 `spin_once()`，~100架/s | 10,000,000架×10Hz = 1亿msg/s | **100万倍** |
| **DDS 组播** | 仅限局域网，无法跨公网 | 需要跨公网/跨机房部署 | **架构性限制** |
| **HTTP 转发** | 同步POST，~200 req/s | 需要百万批次/s | **5000倍** |
| **Spring Boot** | 单实例，200并发线程 | 需要水平扩展到1000+实例 | **1000倍** |
| **STOMP SimpleBroker** | 内存broker，单实例 | 需要分布式broker | **无法扩展** |
| **PostgreSQL写入** | JPA saveAll，~1000条/批/5s | 需要100万条/s写入 | **5000倍** |
| **Redis** | 单实例，~10万key | 5000万key + 1亿次/s读写 | **需要集群** |

## 二、核心问题汇总

### 2.1 DDS 组播限制（最根本的架构问题）

**问题**：DDS 基于 UDP 组播（multicast）进行节点发现和数据传输，组播流量无法跨越路由器/NAT/公网。

**影响**：
- 所有 PX4 无人机和 DDS Gateway 必须在同一局域网内
- 无法支持跨城市、跨机房的分布式无人机集群
- 无法支持通过 4G/5G 网络连接的无人机
- 随着无人机数量增加，组播流量会导致网络拥塞

**当前代码体现**（`dds_gateway.py:121-162`）：
```python
# 当前: 依赖ROS2默认DDS组播发现
rclpy.init(args=None)
self._node = rclpy.create_node('dds_gateway')
# 无法跨公网, 无法跨子网
```

### 2.2 单点故障

- **Gateway**：单Python进程，崩溃则所有无人机数据中断
- **Backend**：单Spring Boot实例，重启则所有WebSocket连接断开
- **Redis**：单实例，宕机则在线状态全部丢失
- **PostgreSQL**：单实例，无读写分离

### 2.3 消息有序性缺失

- HTTP POST 无序号，多实例部署时同一无人机的消息可能乱序到达
- `ConcurrentLinkedQueue` 无界队列，高负载时消息积压顺序混乱
- 并发命令竞争：Gateway 的 `BaseHTTPRequestHandler` 多线程无锁，同一无人机的两个命令可能交叉执行

### 2.4 过期消息处理缺失

- `DroneState` 缓存无代际ID（epoch），断电重连后旧缓存数据继续发送
- Backend 的 `DDSGatewayController.receiveTelemetry()` 不校验消息时间戳
- 无人机重连后会消费断电前的旧状态数据（armed=true、旧坐标等）

### 2.5 事件与流式数据混合

- armed 状态变化（事件型，需要即时性）和位置更新（流式，需要高吞吐）走同一通道
- 无优先级区分，高频遥测数据可能延迟低频但重要的状态事件

### 2.6 扩展性瓶颈

- `rclpy.spin_once()` 单线程处理所有无人机回调，无法利用多核
- `discover_drones_from_topics()` 每10个cycle扫描一次，新无人机发现延迟最长20秒
- 订阅失败无重试（`if sub_key in self._subscriptions` 去重检查阻止重试）

### 3.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **Zenoh替代DDS** | 解决组播限制，支持跨公网/跨机房部署，兼容现有ROS2话题 |
| **按uav_id分区** | 同一无人机的所有数据路由到同一Kafka分区，天然保证有序性 |
| **事件/流分离** | armed变化、连接/断开等走 `events.drone`（低延迟），位置/速度走 `telemetry.raw`（高吞吐） |
| **无状态服务** | 所有业务服务无状态，通过Kafka Consumer Group自动负载均衡 |
| **背压传导** | Kafka分区→Consumer拉模式，天然背压；WebSocket推送设Rate Limiter |
| **消息代际** | 每条消息携带 `epoch`（无人机启动序号），接收端丢弃旧epoch消息 |
| **视口裁剪** | 前端只订阅当前视口范围内的无人机数据，避免千万级数据全量推送 |

## 四、Zenoh 迁移方案

### 4.1 为什么需要迁移到 Zenoh

**DDS 的根本限制**：

| 问题 | DDS 现状 | Zenoh 解决方案 |
|------|---------|--------------|
| **组播依赖** | 基于UDP组播，无法跨路由器/NAT | 支持TCP/QUIC/TLS，天然穿越NAT |
| **公网传输** | 无法跨公网，需要VPN隧道 | 原生支持WAN路由，无需VPN |
| **发现开销** | 组播发现流量随节点数量平方增长 | 集中式路由器发现，O(1)开销 |
| **跨域通信** | ROS_DOMAIN_ID隔离，跨域需要Bridge | 统一key-space，天然跨域 |
| **嵌入式支持** | 资源消耗大，不适合MCU | Zenoh-Pico最小300字节，支持MCU |
| **性能** | UDP组播在局域网快，WAN场景差 | 比DDS快2倍，比Kafka快50倍 |

**性能对比**（来源：NTU研究论文，2023）：

| 协议 | 单机吞吐量 | 多机吞吐量 | 延迟 |
|------|----------|----------|------|
| DDS (CycloneDDS) | ~30 Gbps | ~25 Gbps | 最低（局域网UDP） |
| **Zenoh** | **67 Gbps** | **51 Gbps** | 低（WAN场景优于DDS） |
| MQTT | ~1 Gbps | ~1 Gbps | 中 |
| Kafka | ~1.3 Gbps | ~1 Gbps | 高 |

### 4.2 Zenoh 架构模式

Zenoh 支持三种部署模式，可灵活组合：

```
模式1: Peer-to-Peer (局域网, 替代当前DDS组播)
  PX4 ──Zenoh-Pico──► Gateway (同一局域网, 直连)

模式2: Client-Router (跨网段, 解决公网问题)
  PX4 ──Zenoh-Pico──► Zenoh Router ──TCP/QUIC──► Gateway (跨公网)

模式3: Router-to-Router (大规模分布式)
  区域1 Zenoh Router ──WAN──► 中心 Zenoh Router ──► Gateway Cluster
  区域2 Zenoh Router ──WAN──► 中心 Zenoh Router
```

### 4.3 PX4 + Zenoh 集成方案

**PX4 v1.17+ 已原生支持 Zenoh-Pico**（PR #24476 已合并）：

```bash
# PX4 飞控端配置 (替代当前的 uXRCE-DDS Agent)
param set ZENOH_ENABLE 3                          # 启用Zenoh
zenoh config net client tcp/192.168.1.100:7447    # 连接Zenoh Router
# 支持TCP/UDP/QUIC, 可跨公网
```

**Zenoh Router 部署**（替代当前的 ROS2 DDS 发现机制）：

```bash
# 每个区域部署一个或多个Zenoh Router
zenohd --config router.json5
# router.json5 配置:
# {
#   "listen": { "endpoints": ["tcp/0.0.0.0:7447"] },
#   "connect": { "endpoints": ["tcp/central-router:7447"] },  # 连接中心路由
#   "plugins": { "ros2dds": {} }  # 可选: 兼容现有ROS2节点
# }
```

### 4.4 DDS → Zenoh 迁移路径（兼容现有代码）

**过渡方案**：使用 `zenoh-plugin-dds` 桥接，无需修改现有 ROS2 代码：

```
阶段1 (过渡期): DDS + Zenoh Bridge
  PX4 ──DDS(局域网)──► zenoh-bridge-dds ──Zenoh──► Gateway
  优点: 现有dds_gateway.py代码无需修改
  缺点: 仍依赖局域网DDS

阶段2 (目标): 纯Zenoh
  PX4 ──Zenoh-Pico(跨公网)──► Zenoh Router ──► Gateway(改用zenoh-python)
  优点: 完全摆脱DDS组播限制
  缺点: 需要修改dds_gateway.py
```

**阶段2 Gateway 代码改造**（`dds_gateway.py` 核心改动）：

```python
# 当前代码: 依赖rclpy/ROS2/DDS
import rclpy
from rclpy.node import Node
node = rclpy.create_node('dds_gateway')
# 订阅DDS话题 (组播, 仅局域网)
sub = node.create_subscription(VehicleGlobalPosition,
    f'/{uav_id}/fmu/out/vehicle_global_position',
    callback, qos_profile)

# 改造后: 使用zenoh-python (支持跨公网)
import zenoh
session = zenoh.open(zenoh.Config.from_file('gateway.json5'))
# 订阅Zenoh key expression (TCP/QUIC, 可跨公网)
sub = session.declare_subscriber(
    f'{uav_id}/fmu/out/vehicle_global_position',
    lambda sample: on_global_position(uav_id, sample)
)
# 发布命令 (替代DDS publish)
pub = session.declare_publisher(f'{uav_id}/fmu/in/vehicle_command')
pub.put(serialize_vehicle_command(cmd))
```

### 4.5 Zenoh 对整体架构的影响

引入 Zenoh 后，架构的变化：

| 层级 | 变化前 | 变化后 | 影响 |
|------|--------|--------|------|
| **无人机通信** | DDS组播(局域网) | Zenoh-Pico(跨公网) | 支持全球部署 |
| **Gateway** | rclpy ROS2节点 | zenoh-python客户端 | 代码重构，逻辑不变 |
| **网络要求** | 必须同一局域网 | 只需TCP/UDP可达 | 支持4G/5G/卫星 |
| **发现机制** | DDS组播发现 | Zenoh Router集中发现 | 发现更快更可靠 |
| **Kafka集成** | 不变 | 不变 | 无影响 |
| **Backend** | 不变 | 不变 | 无影响 |
| **Frontend** | 不变 | 不变 | 无影响 |

**结论**：Zenoh 迁移主要影响 **无人机侧** 和 **Gateway 层**，Kafka 以上的所有服务（Backend、Frontend、数据库）均不受影响，可以并行推进。

## 五、各层详细设计

### 5.1 Edge Layer — Gateway 集群化

**当前文件**：`dds-gateway/dds_gateway.py`（单进程，1492行）

**改造目标**：拆分为可水平扩展的无状态 Gateway Pod

```
改造前:
  dds_gateway.py (单进程, 单ROS2 Node, 处理所有无人机)
  ├── discover_drones_from_topics()   # 发现所有无人机
  ├── subscribe_to_drone()            # 订阅所有话题
  ├── spin_once() → build_payload()  # 单线程处理
  └── HTTP POST → Backend             # 同步转发

改造后:
  gateway-service/ (K8s Deployment, 每Pod一个Zenoh Session)
  ├── DroneAssignmentService          # 从配置/注册中心获取本Pod负责的无人机范围
  ├── ZenohSubscriber                 # 多线程Zenoh订阅 + 本地Ring Buffer
  ├── EventDetector                   # 检测armed变化/连接断开等事件
  ├── KafkaProducer                   # 异步写Kafka (按uav_id做partition key)
  └── CommandConsumer                 # 从Kafka消费命令并通过Zenoh发送给PX4
```

**Kafka 异步写入替代 HTTP POST**：

```python
# 当前代码 (dds_gateway.py:548-584)
def send_to_backend(self, payload: dict) -> bool:
    resp = requests.post(f"{self.backend_url}/api/v1/dds-gateway/telemetry",
                         json=payload, timeout=5)  # 同步HTTP, 单点

# 改造后: Kafka异步写入
from confluent_kafka import Producer

class TelemetryPublisher:
    def __init__(self, kafka_brokers: str):
        self.producer = Producer({
            'bootstrap.servers': kafka_brokers,
            'linger.ms': 5,           # 5ms聚合批次
            'batch.size': 65536,      # 64KB批次
            'compression.type': 'lz4',
            'acks': 1,                # 遥测数据acks=1够了
        })

    def publish_telemetry(self, uav_id: str, data: dict):
        # uav_id做partition key → 同一无人机消息严格有序
        self.producer.produce(
            topic='telemetry.raw',
            key=uav_id.encode(),
            value=json.dumps(data).encode(),
        )

    def publish_event(self, uav_id: str, event_type: str, data: dict):
        # 事件走独立topic, 优先级更高
        data['eventType'] = event_type
        data['epoch'] = self.drone_epochs.get(uav_id, 0)
        self.producer.produce(
            topic='events.drone',
            key=uav_id.encode(),
            value=json.dumps(data).encode(),
        )
```

**水平扩展策略**：
- 每个 Gateway Pod 通过环境变量 `DRONE_RANGE_START`/`DRONE_RANGE_END` 配置负责的无人机范围
- 使用 Consistent Hashing 将 `uav_id` 映射到 Gateway Pod
- K8s HPA 根据 CPU/消息堆积自动扩缩容
- 每个 Pod 连接对应区域的 Zenoh Router

### 5.2 Message Broker Layer — Kafka 集群

**Kafka Topic 设计**：

```
telemetry.raw          # 遥测流 (位置/速度/高度/姿态/电量)
├── 分区数: 1000        # 每分区~10000架无人机
├── 副本因子: 3         # 3副本高可用
├── 保留时间: 1小时      # 实时数据不需要长保留
├── 压缩: LZ4           # 低CPU开销
└── 分区键: uav_id      # 保证单机有序

events.drone            # 事件流 (armed变化/连接/断开/告警)
├── 分区数: 100
├── 副本因子: 3
├── 保留时间: 24小时     # 事件需要更长保留用于审计
└── 分区键: uav_id

commands.down           # 下行命令 (Backend→Gateway→PX4)
├── 分区数: 100
├── 副本因子: 3
├── 保留时间: 10分钟     # 命令有时效性
└── 分区键: uav_id      # 命令路由到负责该无人机的Gateway

commands.ack            # 命令确认 (PX4→Gateway→Backend)
├── 分区数: 100
├── 副本因子: 3
└── 分区键: uav_id
```

**为什么选 Kafka 而不是 Redis Streams**：

| 特性 | Redis Streams | Apache Kafka |
|------|--------------|-------------|
| 存储方式 | 内存（有限） | 磁盘顺序写（无限） |
| 千万级消息 | 内存开销巨大 | 磁盘廉价，可扩展 |
| 吞吐量 | ~100万msg/s | ~500万msg/s（5 Broker） |
| 消息回放 | 支持（有限） | 支持（任意offset） |
| 分区有序 | 支持 | 支持 |
| 生态 | 一般 | 丰富（Kafka Connect等） |
| **推荐** | 万级以下 | **千万级首选** |

#### 5.3.1 telemetry-ingest-service（遥测接入服务）

**替代当前**：`DDSGatewayController.receiveTelemetry()`

核心改动：
- 从 HTTP 接收改为 Kafka Consumer 消费
- 新增过期消息检测（timestamp 校验）
- 新增代际检查（epoch 校验，防止断电重连消费旧数据）
- 更新 Redis 最新状态

```java
@KafkaListener(topics = "telemetry.raw",
               groupId = "ingest-group",
               concurrency = "32")  // 32个消费线程, 匹配Kafka分区数
public void onTelemetry(ConsumerRecord<String, String> record) {
    String uavId = record.key();
    TelemetryMessage msg = deserialize(record.value());

    // 1. 过期消息检测 (关键新增)
    long msgAge = System.currentTimeMillis() - msg.getTimestamp();
    if (msgAge > MAX_AGE_MS) {  // 默认5秒
        metrics.counter("telemetry.stale.dropped").increment();
        return;
    }

    // 2. 代际检查 (关键新增, 防止断电重连消费旧数据)
    long currentEpoch = droneEpochCache.getOrDefault(uavId, 0L);
    if (msg.getEpoch() < currentEpoch) {
        log.warn("Stale epoch for {}: msg={} current={}", uavId, msg.getEpoch(), currentEpoch);
        return;
    }

    // 3. 更新Redis最新状态 (替代当前的setDroneOnline)
    redisCluster.hset("drone:" + uavId + ":state", buildStateMap(msg));
    redisCluster.expire("drone:" + uavId + ":state", 30);

    // 4. 转发到push topic供实时推送服务消费
    kafkaTemplate.send("telemetry.partitioned", uavId, record.value());
}
```

#### 5.3.2 realtime-push-service（实时推送服务）

**替代当前**：`WebSocketGatewayService.java` + `WebSocketConfig.java`

#### 5.3.3 telemetry-store-service（遥测存储服务）

**替代当前**：`TelemetryPersistenceService.java`

当前问题：
- `ConcurrentLinkedQueue` 无界队列，OOM 风险
- JPA `saveAll()` 逐条 INSERT，性能差
- PostgreSQL 单表无分区，查询慢
- 5秒 flush 间隔，高负载时堆积严重

改造方案：
- Kafka Consumer 按批次消费（自带背压）
- TimescaleDB hypertable 自动按时间分区
- COPY 批量写入，单表100万行/s

**数据库选型对比**：

| 特性 | PostgreSQL（当前） | TimescaleDB | ClickHouse |
|------|-----------------|-------------|------------|
| 写入速度 | ~5000行/s | ~50万行/s | ~200万行/s |
| 压缩比 | 1:1 | 5:1 | 10:1 |
| 实时查询 | 慢（无分区） | 快（自动分区） | 极快（列存） |
| 聚合查询 | 慢 | 快（连续聚合） | 极快 |
| 与PG兼容 | ✅ | ✅（完全兼容） | ❌ |
| 运维复杂度 | 低 | 中 | 高 |
| **推荐** | ❌ 不适合千万级 | ✅ **首选** | ✅ 备选 |

#### 5.3.4 drone-state-service（无人机状态管理服务）

**替代当前**：`PartitionRoutingService.java` + `RedisService.java`

**Redis Cluster Key 设计**（替代当前多个独立 key）：

```
# 每架无人机的完整状态 (一个Hash, 替代当前3-5个独立key)
drone:{uav_id}:state
├── lat, lon, alt, heading, speed     # 最新位置
├── armed, flightMode                 # 飞行状态
├── epoch                             # 代际ID (每次启动递增)
├── lastUpdate                        # 最后更新时间戳
├── gatewayId                         # 负责的Gateway Pod ID
└── partitions                        # 所属分区列表 (JSON数组)

# 分区反向索引 (不变)
partition:{name}:drones → Set<uav_id>

# 命令锁 (改用Redlock算法, 支持多节点)
lock:drone:{uav_id} → lockValue (5s TTL)
```

**断电重连处理（epoch机制）**：

```
T0: drone px4_1 运行中, epoch=5, armed=true
T1: drone px4_1 断电
    → Gateway检测到Zenoh连接断开
    → 发送事件: {type: "DISCONNECTED", uav_id: px4_1, epoch: 5}
    → State Service清除px4_1的Redis状态

T2: drone px4_1 重新上电, 新epoch=6
    → Gateway检测到Zenoh连接建立
    → 发送事件: {type: "CONNECTED", uav_id: px4_1, epoch: 6}
    → State Service重置状态: armed=false, mode=MANUAL

T3: 如果收到旧消息: {uav_id: px4_1, epoch: 5, armed: true}
    → epoch(5) < 当前epoch(6), 丢弃! ← 关键保护
```

#### 5.3.5 command-service（命令下发服务）

**替代当前**：`ControlService.java` + `DdsCommandService.java`

当前问题：
- 同步 HTTP 调用，Gateway 不可达则命令丢失
- 无重试、无确认机制、无命令去重
- 并发命令竞争（Gateway 的 `BaseHTTPRequestHandler` 多线程无锁）

改造方案：

```java
// 命令写入Kafka (替代当前的HTTP POST)
public CompletableFuture<String> sendCommand(String uavId, String commandType,
                                              String params) {
    CommandMessage cmd = CommandMessage.builder()
        .commandId(UUID.randomUUID().toString())  // 幂等key
        .uavId(uavId)
        .commandType(commandType)
        .params(params)
        .timestamp(Instant.now())
        .expireAt(Instant.now().plusSeconds(10))   // 10秒过期
        .build();

    // 写入Kafka, uav_id做partition key → 命令有序
    return kafkaTemplate.send("commands.down", uavId, toJson(cmd))
        .thenApply(result -> cmd.getCommandId());
}

// Gateway消费命令并执行
@KafkaListener(topics = "commands.down", groupId = "gateway-command-group")
public void onCommand(ConsumerRecord<String, String> record) {
    CommandMessage cmd = deserialize(record.value());
    // 检查命令是否过期
    if (Instant.now().isAfter(cmd.getExpireAt())) {
        log.warn("Command expired: {}", cmd.getCommandId());
        return;
    }
    // 通过Zenoh发送给PX4 (替代当前的DDS publish)
    zenohSession.put(cmd.getUavId() + "/fmu/in/vehicle_command",
                     serializeVehicleCommand(cmd));
}

// ACK消费者
@KafkaListener(topics = "commands.ack", groupId = "command-ack-group")
public void onCommandAck(ConsumerRecord<String, String> record) {
    CommandAck ack = deserialize(record.value());
    commandLogRepository.updateStatus(ack.getCommandId(),
        ack.isSuccess() ? "ACK_SUCCESS" : "ACK_FAILED");
    messagingTemplate.convertAndSend("/topic/command-ack", ack);
}
```

## 六、消息有序性保证

### 6.1 Kafka 分区有序性原理

```
Producer写入 (按uav_id分区):
  drone px4_1 msg1 ──┐
  drone px4_1 msg2 ──┤  Partition 0 (负责px4_1):
  drone px4_1 msg3 ──┘  [msg1, msg2, msg3]  ──► Consumer Thread #0
                                                  严格按序消费

  drone px4_2 msg1 ──┐
  drone px4_2 msg2 ──┘  Partition 1 (负责px4_2):
                         [msg1, msg2]        ──► Consumer Thread #1
                                                  与px4_1独立并行
```

**保证机制**：
1. **生产端**：`producer.send(topic, key=uav_id, value=data)` — 相同 key 总是路由到同一分区
2. **Broker 端**：同一分区内消息严格按写入顺序存储，不会重排
3. **消费端**：Kafka 保证同一分区只被 Consumer Group 中的一个 Consumer 消费

### 6.2 跨服务有序性

```
telemetry.raw (Partition 0, 负责 px4_1):
  offset=100: {uav_id: px4_1, lat: 39.9,  armed: false, epoch: 5}
  offset=101: {uav_id: px4_1, lat: 39.91, armed: true,  epoch: 5}  ← armed变化
  offset=102: {uav_id: px4_1, lat: 39.92, armed: true,  epoch: 5}

ingest-service Consumer Thread #0 (绑定Partition 0):
  处理 offset=100 → Redis: armed=false
  处理 offset=101 → Redis: armed=true   ← 有序!
  处理 offset=102 → Redis: armed=true

push-service Consumer Thread #0 (也绑定Partition 0):
  处理 offset=100 → WebSocket: armed=false
  处理 offset=101 → WebSocket: armed=true  ← 有序!
```

### 6.3 命令有序性

```
commands.down (Partition 0, 负责 px4_1):
  offset=50: {cmd: ARM,     uavId: px4_1, commandId: abc}
  offset=51: {cmd: TAKEOFF, uavId: px4_1, commandId: def}
  offset=52: {cmd: GOTO,    uavId: px4_1, commandId: ghi}

Gateway Consumer (绑定Partition 0):
  执行 ARM    → 等待ACK
  执行 TAKEOFF → 等待ACK
  执行 GOTO   → 等待ACK
  严格按序执行, 不会出现GOTO先于ARM执行的情况
```

## 附录：关键问题解答

### Q1：大幅调整是否必须用 Kafka？

在千万级场景下，**Kafka 是最合适的选择**：
1. **单分区严格有序** — 按 uav_id 分区，天然保证同一无人机消息有序
2. **百万级吞吐** — 单 Broker 100万msg/s，10个 Broker 能支撑1000万msg/s
3. **持久化+回放** — 消息落盘，Consumer 可从任意 offset 重新消费（故障恢复）
4. **生态成熟** — Kafka Connect 对接各种存储，Spring Kafka 深度集成

如果是万级无人机，Redis Streams 或 gRPC Streaming 也够用。但**千万级 + 有序性 + 高可用 + 持久化**，Kafka 是业界标准方案。

### Q2：Zenoh 会影响 Kafka 以上的架构吗？

**不会**。Zenoh 只影响 **无人机侧** 和 **Gateway 层**：
- Kafka 以上的所有服务（Backend、Frontend、数据库）完全不受影响
- Gateway 从 `rclpy.subscribe()` 改为 `zenoh.subscribe()`，业务逻辑不变
- 可以使用 `zenoh-bridge-dds` 作为过渡，现有 `dds_gateway.py` 代码无需修改

### Q3：幽灵指令和轨迹偏差问题会被解决吗？

**会**，通过以下机制：
1. **命令有序性**：Kafka 按 uav_id 分区，同一无人机的命令严格按序执行
2. **命令锁**：Redis 分布式锁防止并发命令竞争
3. **命令过期**：命令携带 `expireAt`，超时未执行自动丢弃
4. **ACK 确认**：命令执行结果通过 `commands.ack` topic 反馈，前端可显示真实执行状态

### Q4：断电重连的过期数据问题会被解决吗？

**会**，通过 epoch 代际机制：
- 每次无人机连接分配新 epoch（递增整数）
- 所有消息携带 epoch
- 接收端丢弃 epoch 小于当前值的消息
- 断电重连时 State Service 重置所有缓存状态（armed=false 等）
