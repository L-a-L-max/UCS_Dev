## 1. Kafka 消息队列引入

### 【痛点描述】

原架构中，DDS Gateway（Python）通过 HTTP POST 直接将遥测数据发送到 Spring Boot 后端：

```
PX4 → DDS → Python Gateway --HTTP POST--> Spring Boot → DB + WebSocket
```

**三个核心问题：**

| # | 问题 | 严重程度 | 具体表现 |
|---|------|----------|----------|
| P3 | 消息乱序 | 高 | 多架无人机数据混在一个 HTTP 请求中，无法保证单架无人机消息顺序 |
| P4 | 过期消息 | 高 | 无人机重连后，旧连接的残留消息仍被处理，导致"僵尸数据" |
| P5 | 事件流混合 | 中 | 遥测、事件、指令回执全部走同一个 HTTP 通道，无法独立扩缩 |

**源码证据：**

```java
// DDSGatewayController.java (改造前)
// 所有无人机的遥测数据混在一个 List 中，按顺序处理
// 如果 px4_1 和 px4_2 的数据交织，无法保证单架无人机的时序
for (Map<String, Object> droneData : drones) {
    telemetryPersistenceService.persistFromMap(droneData);  // 直接写DB
    webSocketGatewayService.broadcastToPartitions(...)       // 直接推送
}
```

### 【技术选型】

**为什么选 Kafka 而不是其他消息队列？**

| 消息队列 | 吞吐量 | 消息顺序 | 持久化 | 适合场景 |
|----------|--------|----------|--------|----------|
| **Kafka** | **100万+/s** | **分区内有序** | **磁盘持久** | **高吞吐、有序流** |
| RabbitMQ | 5万/s | 队列内有序 | 内存优先 | 业务消息、RPC |
| Redis Stream | 10万/s | 单流有序 | 可选 | 轻量级流处理 |
| Pulsar | 100万+/s | 分区内有序 | 分层存储 | 多租户、跨地域 |

**选择 Kafka 的决定性因素：**

1. **分区机制天然匹配无人机模型** — 以 `uav_id` 作为 Partition Key，同一架无人机的所有消息进入同一分区，保证有序
2. **吞吐量满足千万级** — 单集群轻松支撑百万 TPS
3. **消费者组弹性** — Consumer 数量可动态调整，不影响生产者
4. **持久化回溯** — 消息保留 7 天，出问题可回溯排查

### 【底层原理（小白看这里）】

#### Kafka 消息顺序保证原理

```
想象一个邮局（Kafka Broker），有 16 个分拣窗口（Partition）。

每架无人机（uav_id）是一个固定寄信人。
寄信人会被分配到固定窗口：hash("px4_1") % 16 = 窗口3

窗口内的信件（消息）严格按到达顺序排列。
所以 px4_1 的所有消息在窗口3中是有序的。

但 px4_1（窗口3）和 px4_2（窗口7）之间没有顺序关系——
这正好符合我们的需求：不同无人机之间不需要排序。
```

```
                         Kafka Broker
                    ┌─────────────────┐
px4_1 ──key="px4_1"──→ │ Partition 3    │ → Consumer A (处理 px4_1 的遥测)
                    │ [msg1][msg2][msg3]│
                    ├─────────────────┤
px4_2 ──key="px4_2"──→ │ Partition 7    │ → Consumer B (处理 px4_2 的遥测)
                    │ [msg1][msg2][msg3]│
                    └─────────────────┘

关键: 分区内有序 ✓  跨分区无序（不需要）✓
```

#### 为什么 HTTP 不能保证顺序？

```
Gateway 批量发送:
POST /telemetry  { drones: [px4_1_数据, px4_2_数据, px4_1_数据] }
                                                    ↑
                            px4_1 的两条数据被 px4_2 打断
                            后端处理时可能因线程调度导致乱序
```

### 【常见疑问 (Q&A)】

**Q1: Kafka 挂了怎么办？**
> Gateway 采用**双写模式**：优先写 Kafka，Kafka 失败自动降级到 HTTP 直连。见 `dds_gateway.py` 的 `run()` 方法中的 dual-write 逻辑。

**Q2: 分区数为什么是 16？**
> telemetry.raw 设置 16 个分区，是因为消费者数量上限 = 分区数。16 个分区允许最多 16 个并发消费者，满足早期千级无人机的处理需求。后续可动态扩分区。

**Q3: 本地开发怎么启动 Kafka？**
> ```bash
> docker-compose -f docker-compose-kafka.yml up -d
> # Kafka UI: http://localhost:8090
> # Kafka Broker: localhost:9092
> ```

**Q4: 如何确认消息正常流转？**
> 打开 Kafka UI (http://localhost:8090)，查看各 Topic 的消息数量和消费者 Lag。

## 2. Epoch 机制（消息世代管理）

### 【痛点描述】

无人机重连场景下，旧连接的残留消息可能迟到，导致"僵尸数据"覆盖新数据：

```
时间线:
  t1: px4_1 连接（epoch=1），发送消息 A
  t2: px4_1 断开
  t3: px4_1 重连（epoch=2），发送消息 B
  t4: 消息 A 才到达（网络延迟）
  
  问题: 如果不检查 epoch，消息 A 会覆盖消息 B，导致数据回退！
```

### 【技术选型】

**Epoch（世代号）机制**：每次无人机连接时递增一个世代号，消费端只接受 >= 当前世代的消息。

这是分布式系统中经典的 **Generation ID / Fencing Token** 模式，Kafka 自身的 Consumer Rebalance 也使用类似机制。

### 【底层原理（小白看这里）】

```
想象你换了新手机号（epoch=2），但旧手机号（epoch=1）的短信还在路上。

当你收到一条短信时，检查它是来自哪个手机号：
  - epoch=2（新号）→ 接受 ✓
  - epoch=1（旧号）→ 丢弃 ✗（过时数据）

EpochManager 就是做这件事的：
  1. 记录每架无人机当前的 epoch
  2. 每条消息到达时，检查消息的 epoch >= 当前 epoch
  3. 不满足则丢弃
```

```
                EpochManager
                ┌────────────────┐
                │ px4_1 → epoch=2│
                │ px4_2 → epoch=1│
                └───────┬────────┘
                        │
  消息到达 ─────────────┤
  {uavId:"px4_1",       │
   epoch:1,             │
   data:...}            │
                        ▼
              epoch(1) < current(2)
              → 丢弃！"僵尸消息"
```

### 【实现细节】

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| Epoch 管理器 | `kafka/EpochManager.java` | 维护每架无人机的当前 epoch |
| Epoch 验证 | `kafka/TelemetryKafkaConsumer.java` | 消费时校验 epoch |
| Epoch 递增 | `dds-gateway/dds_gateway.py` | 发现新/重连无人机时递增 epoch |

#### EpochManager 核心逻辑

```java
// EpochManager.java
public boolean validateEpoch(String uavId, int messageEpoch) {
    int currentEpoch = epochMap.getOrDefault(uavId, 0);
    if (messageEpoch > currentEpoch) {
        // 新世代：更新
        epochMap.put(uavId, messageEpoch);
        return true;
    }
    return messageEpoch >= currentEpoch;  // 相等也接受（正常消息）
}
```

#### Gateway 端 Epoch 递增

```python
# dds_gateway.py
def _get_or_increment_epoch(self, uav_id: str, is_new: bool = False) -> int:
    if uav_id not in self._epoch_map:
        self._epoch_map[uav_id] = 1
    elif is_new:
        self._epoch_map[uav_id] += 1  # 重连时递增
    return self._epoch_map[uav_id]
```

### 【常见疑问 (Q&A)】

**Q1: Epoch 值会不会溢出？**
> 理论上 int 最大值 21 亿。假设无人机每秒重连一次（极端情况），也需要 68 年才会溢出。实际生产中完全不用担心。

**Q2: Gateway 重启后 epoch 怎么办？**
> Gateway 重启时 epoch 从 0 开始。但因为所有无人机也会重新发现（new drone），epoch 会被重新分配为 1。消费端的 EpochManager 也会因为 `messageEpoch > currentEpoch` 而接受新世代。

**Q3: 多个 Gateway 实例怎么协调 epoch？**
> 当前单 Gateway 实例无需协调。未来多 Gateway 部署时，需要将 epoch 存储在 Redis 中（原子递增 `INCR drone:{uavId}:epoch`），替代本地 HashMap。

## 3. 双 Token 三验证认证体系

### 【痛点描述】

原系统使用**单 JWT Token** 认证：

```java
// 改造前: JwtUtil.java
jwt.expiration=86400000  // 24小时过期
```

**三个核心问题：**

| # | 问题 | 风险 | 说明 |
|---|------|------|------|
| 1 | Token 有效期过长 | 高 | 24小时内 token 被盗取则无法撤销 |
| 2 | 无法主动注销 | 高 | 用户退出登录后 token 仍然有效 |
| 3 | 无法区分 token 用途 | 中 | 同一个 token 既用于接口鉴权也可用于刷新，攻击面大 |

**攻击场景：**

```
1. 用户在公共电脑登录，忘记退出
2. 攻击者获取到 token（24小时有效）
3. 即使用户在手机上"退出登录"，攻击者的 token 仍然有效
4. 24小时内攻击者可以任意操控无人机 → 严重安全隐患
```

### 【技术选型】

**双 Token 三验证方案：**

| 机制 | 说明 |
|------|------|
| **Access Token** | 短命（30分钟），用于接口鉴权 |
| **Refresh Token** | 长命（7天），仅用于刷新 Access Token |
| **验证1: 签名验证** | HMAC-SHA 签名校验，防止篡改 |
| **验证2: 过期验证** | exp 时间戳检查 |
| **验证3: 黑名单验证** | Redis 存储已注销 token，实时拦截 |

**为什么不用 OAuth2 / Session？**

| 方案 | 优势 | 劣势（对本项目） |
|------|------|---------|
| 单 JWT | 简单 | 无法注销、有效期过长 |
| **双 JWT + Redis 黑名单** | **平衡安全与简洁** | **Redis 依赖（已有）** |
| OAuth2 全套 | 标准化 | 过重，需要额外的 Authorization Server |
| Session | 服务端状态 | 不适合无状态微服务架构 |

### 【底层原理（小白看这里）】

```
想象一个公司的门禁系统:

Access Token = 临时访客证（30分钟有效）
  - 进入每个房间都要刷这个卡
  - 过期了就不能用了
  - 被偷了最多损失30分钟

Refresh Token = 员工工牌（7天有效）
  - 不能直接开门！
  - 只能去前台（/api/v1/auth/refresh）换取新的访客证
  - 相当于"我还在职"的证明

三验证:
  1. 签名验证 = 检查卡片防伪标记（有没有被伪造？）
  2. 过期验证 = 检查有效期（过期了吗？）
  3. 黑名单验证 = 检查黑名单（被注销了吗？）
```

```
登录流程:
  用户 → POST /login → 返回 { token: "access...", refreshToken: "refresh..." }

正常请求:
  用户 → GET /api/xxx (Header: Bearer access_token)
       → Filter: 签名✓ 过期✓ 黑名单✓ 类型=access✓ → 放行

Access Token 过期:
  用户 → POST /refresh { refreshToken: "refresh..." }
       → 验证 refresh token → 返回新的 access token

注销:
  用户 → POST /logout (Header: Bearer access_token)
       → 将 access token 加入 Redis 黑名单
       → 前端清除两个 token
```

#### JwtUtil 核心改造

```java
// Token 生成 — 通过 tokenType claim 区分
private String buildToken(Long userId, String username, List<String> roles,
                          String tokenType, long expirationMs) {
    return Jwts.builder()
            .subject(username)
            .claim("userId", userId)
            .claim("roles", roles)
            .claim("tokenType", tokenType)  // "access" 或 "refresh"
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + expirationMs))
            .signWith(getSigningKey())
            .compact();
}

// 三验证
public Boolean validateToken(String token, String username) {
    extractUsername(token);       // 验证1: 签名（extractAllClaims 内部校验）
    if (isTokenExpired(token))    // 验证2: 过期
        return false;
    if (isTokenBlacklisted(token)) // 验证3: 黑名单（Redis）
        return false;
    return true;
}
```

#### Redis 黑名单实现

```java
// 黑名单 Key 格式: token:blacklist:{jwt_string}
// TTL = token 剩余有效时间（到期自动清除，避免 Redis 无限膨胀）

public void blacklistToken(String token) {
    Date expiration = extractExpiration(token);
    long ttlMs = expiration.getTime() - System.currentTimeMillis();
    if (ttlMs > 0) {
        stringRedisTemplate.opsForValue()
            .set("token:blacklist:" + token, "1", ttlMs, TimeUnit.MILLISECONDS);
    }
}
```

### 【常见疑问 (Q&A)】

**Q1: 前端怎么配合？**
> 1. 登录后保存 `token` 和 `refreshToken`
> 2. 每次请求在 Header 中携带 `Authorization: Bearer <access_token>`
> 3. 收到 401 时，调用 `/refresh` 接口用 refreshToken 换取新 accessToken
> 4. 如果 refreshToken 也过期，跳转到登录页

**Q2: Redis 挂了怎么办？**
> 黑名单检查失败时**放行**（`isTokenBlacklisted` 返回 false）。牺牲少量安全性换取可用性。短期内 access token 最多有效 30 分钟，风险可控。

**Q3: 为什么不用 Refresh Token Rotation（旋转刷新）？**
> Rotation 模式下每次刷新都会发新的 refresh token，旧的作废。这增加了复杂度，且需要处理并发刷新冲突。当前 7 天的 refresh token 已经足够安全，后续有需要可以升级。

**Q4: 旧版本 token（没有 tokenType 字段）还能用吗？**
> 兼容。`isTokenType()` 方法中，如果 token 没有 `tokenType` 字段，默认视为 `access` 类型。升级后旧 token 在过期前仍然有效。

## 4. 租户隔离方案分析

### 【痛点描述】

当前系统通过**分区（Partition）**实现了同一团队内的用户数据隔离，但**不同组织/企业之间没有数据隔离**：

```
现状：
  企业A 的用户 和 企业B 的用户 → 共享同一张 drones 表
  企业A 的管理员 → 理论上能看到企业B的无人机
```

### 【技术选型】

推荐 **共享表 + 行级过滤（Row-Level Security）** 方案：
- 在所有业务表添加 `tenant_id` 字段
- 利用 Hibernate Filter 自动在所有查询中注入 `WHERE tenant_id = ?`
- 通过 ThreadLocal（TenantContext）传播租户上下文

### 【底层原理（小白看这里）】

```
想象一个共享办公楼（数据库），每个公司（租户）租了一层:

  行级过滤 = 每个公司只能看到自己那层的房间（数据行）
  即使在同一张表里，tenant_id 不同就看不到

  SELECT * FROM drones WHERE tenant_id = 1;
  → 企业A 只能看到自己的无人机

  即使有人直接查所有数据:
  Hibernate Filter 会自动加上 WHERE tenant_id = 当前用户的租户ID
```

### 【当前状态】

**租户隔离未在当前阶段实现**，原因：
1. 改动面过大（涉及所有实体和查询）
2. 与 Kafka Phase 1 改造时间冲突
3. 需要数据迁移和前端配合

**详细实现方案见**：[Doc/租户隔离实现方案.md](./租户隔离实现方案.md)

该方案文档包含：
- 完整的数据库 Schema 变更 SQL
- 应用层改造代码示例（TenantContext、TenantFilter、Hibernate Filter）
- 分步实施路径（4个Phase，约6-8周）

### 【常见疑问 (Q&A)】

**Q1: 分区隔离和租户隔离有什么区别？**
> - **分区隔离（当前已有）**：控制"用户能看到哪些无人机的实时数据"，是功能级隔离
> - **租户隔离（待实现）**：控制"不同企业的数据完全不可见"，是安全级隔离
> - 两者正交：企业A内部仍然用分区管理用户权限

**Q2: 什么时候实现？**
> 建议在 Phase 2（微服务拆分）之后实现，此时每个微服务可独立改造，风险可控。
