## 1. Kafka 消息队列引入

### 【痛点描述】

原架构中，DDS Gateway（Python）通过 HTTP POST 直接将遥测数据发送到 Spring Boot 后端：

```
PX4 → DDS → Python Gateway --HTTP POST--> Spring Boot → DB + WebSocket
```

**三个核心问题：**

| # | 问题 | 严重程度 | 具体表现 |
|---|------|----------|----------|
| P3 | 消息乱序 | 高 | 多架无人机数据混在一个 HTTP 请求中，无法保证单架无人机消息顺序 |
| P4 | 过期消息 | 高 | 无人机重连后，旧连接的残留消息仍被处理，导致"僵尸数据" |
| P5 | 事件流混合 | 中 | 遥测、事件、指令回执全部走同一个 HTTP 通道，无法独立扩缩 |

**源码证据：**

```java
// DDSGatewayController.java (改造前)
// 所有无人机的遥测数据混在一个 List 中，按顺序处理
// 如果 px4_1 和 px4_2 的数据交织，无法保证单架无人机的时序
for (Map<String, Object> droneData : drones) {
    telemetryPersistenceService.persistFromMap(droneData);  // 直接写DB
    webSocketGatewayService.broadcastToPartitions(...)       // 直接推送
}
```

### 【技术选型】

**为什么选 Kafka 而不是其他消息队列？**

| 消息队列 | 吞吐量 | 消息顺序 | 持久化 | 适合场景 |
|----------|--------|----------|--------|----------|
| **Kafka** | **100万+/s** | **分区内有序** | **磁盘持久** | **高吞吐、有序流** |
| RabbitMQ | 5万/s | 队列内有序 | 内存优先 | 业务消息、RPC |
| Redis Stream | 10万/s | 单流有序 | 可选 | 轻量级流处理 |
| Pulsar | 100万+/s | 分区内有序 | 分层存储 | 多租户、跨地域 |

**选择 Kafka 的决定性因素：**

1. **分区机制天然匹配无人机模型** — 以 `uav_id` 作为 Partition Key，同一架无人机的所有消息进入同一分区，保证有序
2. **吞吐量满足千万级** — 单集群轻松支撑百万 TPS
3. **消费者组弹性** — Consumer 数量可动态调整，不影响生产者
4. **持久化回溯** — 消息保留 7 天，出问题可回溯排查

### 【底层原理（小白看这里）】

#### Kafka 消息顺序保证原理

```
想象一个邮局（Kafka Broker），有 16 个分拣窗口（Partition）。

每架无人机（uav_id）是一个固定寄信人。
寄信人会被分配到固定窗口：hash("px4_1") % 16 = 窗口3

窗口内的信件（消息）严格按到达顺序排列。
所以 px4_1 的所有消息在窗口3中是有序的。

但 px4_1（窗口3）和 px4_2（窗口7）之间没有顺序关系——
这正好符合我们的需求：不同无人机之间不需要排序。
```

```
                         Kafka Broker
                    ┌─────────────────┐
px4_1 ──key="px4_1"──→ │ Partition 3    │ → Consumer A (处理 px4_1 的遥测)
                    │ [msg1][msg2][msg3]│
                    ├─────────────────┤
px4_2 ──key="px4_2"──→ │ Partition 7    │ → Consumer B (处理 px4_2 的遥测)
                    │ [msg1][msg2][msg3]│
                    └─────────────────┘

关键: 分区内有序 ✓  跨分区无序（不需要）✓
```

#### 为什么 HTTP 不能保证顺序？

```
Gateway 批量发送:
POST /telemetry  { drones: [px4_1_数据, px4_2_数据, px4_1_数据] }
                                                    ↑
                            px4_1 的两条数据被 px4_2 打断
                            后端处理时可能因线程调度导致乱序
```

```
改造前:
  Gateway --HTTP--> DDSGatewayController → DB + WebSocket

改造后:

```

### 【常见疑问 (Q&A)】

**Q1: Kafka 挂了怎么办？**
> Gateway 采用**双写模式**：优先写 Kafka，Kafka 失败自动降级到 HTTP 直连。见 `dds_gateway.py` 的 `run()` 方法中的 dual-write 逻辑。

**Q2: 分区数为什么是 16？**
> telemetry.raw 设置 16 个分区，是因为消费者数量上限 = 分区数。16 个分区允许最多 16 个并发消费者，满足早期千级无人机的处理需求。后续可动态扩分区。

**Q3: 本地开发怎么启动 Kafka？**
> ```bash
> docker-compose -f docker-compose-kafka.yml up -d
> # Kafka UI: http://localhost:8090
> # Kafka Broker: localhost:9092
> ```

**Q4: 如何确认消息正常流转？**
> 打开 Kafka UI (http://localhost:8090)，查看各 Topic 的消息数量和消费者 Lag。

## 2. Epoch 机制（消息世代管理）

### 【痛点描述】

无人机重连场景下，旧连接的残留消息可能迟到，导致"僵尸数据"覆盖新数据：

```
时间线:
  t1: px4_1 连接（epoch=1），发送消息 A
  t2: px4_1 断开
  t3: px4_1 重连（epoch=2），发送消息 B
  t4: 消息 A 才到达（网络延迟）
  
  问题: 如果不检查 epoch，消息 A 会覆盖消息 B，导致数据回退！
```

### 【技术选型】

**Epoch（世代号）机制**：每次无人机连接时递增一个世代号，消费端只接受 >= 当前世代的消息。

这是分布式系统中经典的 **Generation ID / Fencing Token** 模式，Kafka 自身的 Consumer Rebalance 也使用类似机制。

### 【底层原理（小白看这里）】

```
想象你换了新手机号（epoch=2），但旧手机号（epoch=1）的短信还在路上。

当你收到一条短信时，检查它是来自哪个手机号：
  - epoch=2（新号）→ 接受 ✓
  - epoch=1（旧号）→ 丢弃 ✗（过时数据）

EpochManager 就是做这件事的：
  1. 记录每架无人机当前的 epoch
  2. 每条消息到达时，检查消息的 epoch >= 当前 epoch
  3. 不满足则丢弃
```

```
                EpochManager
                ┌────────────────┐
                │ px4_1 → epoch=2│
                │ px4_2 → epoch=1│
                └───────┬────────┘
                        │
  消息到达 ─────────────┤
  {uavId:"px4_1",       │
   epoch:1,             │
   data:...}            │
                        ▼
              epoch(1) < current(2)
              → 丢弃！"僵尸消息"
```

### 【实现细节】

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| Epoch 管理器 | `kafka/EpochManager.java` | 维护每架无人机的当前 epoch |
| Epoch 验证 | `kafka/TelemetryKafkaConsumer.java` | 消费时校验 epoch |
| Epoch 递增 | `dds-gateway/dds_gateway.py` | 发现新/重连无人机时递增 epoch |

#### EpochManager 核心逻辑

```java
// EpochManager.java
public boolean validateEpoch(String uavId, int messageEpoch) {
    int currentEpoch = epochMap.getOrDefault(uavId, 0);
    if (messageEpoch > currentEpoch) {
        // 新世代：更新
        epochMap.put(uavId, messageEpoch);
        return true;
    }
    return messageEpoch >= currentEpoch;  // 相等也接受（正常消息）
}
```

#### Gateway 端 Epoch 递增

```python
# dds_gateway.py
def _get_or_increment_epoch(self, uav_id: str, is_new: bool = False) -> int:
    if uav_id not in self._epoch_map:
        self._epoch_map[uav_id] = 1
    elif is_new:
        self._epoch_map[uav_id] += 1  # 重连时递增
    return self._epoch_map[uav_id]
```

### 【常见疑问 (Q&A)】

**Q1: Epoch 值会不会无限增长？**
> 不会。已实现定期重置机制（见第 6 章），每 6 小时将超过 10000 的 epoch 归一化到 1，超过 24 小时未活跃的无人机自动清除。

**Q2: Gateway 重启后 epoch 怎么办？**
> Gateway 重启时 epoch 从 0 开始。但因为所有无人机也会重新发现（new drone），epoch 会被重新分配为 1。消费端的 EpochManager 也会因为 `messageEpoch > currentEpoch` 而接受新世代。

**Q3: 多个 Gateway 实例怎么协调 epoch？**
> 当前单 Gateway 实例无需协调。未来多 Gateway 部署时，需要将 epoch 存储在 Redis 中（原子递增 `INCR drone:{uavId}:epoch`），替代本地 HashMap。

## 3. 双 Token 三验证认证体系

### 【痛点描述】

原系统使用**单 JWT Token** 认证：

```java
// 改造前: JwtUtil.java
jwt.expiration=86400000  // 24小时过期
```

**三个核心问题：**

| # | 问题 | 风险 | 说明 |
|---|------|------|------|
| 1 | Token 有效期过长 | 高 | 24小时内 token 被盗取则无法撤销 |
| 2 | 无法主动注销 | 高 | 用户退出登录后 token 仍然有效 |
| 3 | 无法区分 token 用途 | 中 | 同一个 token 既用于接口鉴权也可用于刷新，攻击面大 |

**攻击场景：**

```
1. 用户在公共电脑登录，忘记退出
2. 攻击者获取到 token（24小时有效）
3. 即使用户在手机上"退出登录"，攻击者的 token 仍然有效
4. 24小时内攻击者可以任意操控无人机 → 严重安全隐患
```

### 【技术选型】

**双 Token 三验证方案：**

| 机制 | 说明 |
|------|------|
| **Access Token** | 短命（30分钟），用于接口鉴权 |
| **Refresh Token** | 长命（7天），仅用于刷新 Access Token |
| **验证1: 签名验证** | HMAC-SHA 签名校验，防止篡改 |
| **验证2: 过期验证** | exp 时间戳检查 |
| **验证3: 黑名单验证** | Redis 存储已注销 token，实时拦截 |

**为什么不用 OAuth2 / Session？**

| 方案 | 优势 | 劣势（对本项目） |
|------|------|---------|
| 单 JWT | 简单 | 无法注销、有效期过长 |
| **双 JWT + Redis 黑名单** | **平衡安全与简洁** | **Redis 依赖（已有）** |
| OAuth2 全套 | 标准化 | 过重，需要额外的 Authorization Server |
| Session | 服务端状态 | 不适合无状态微服务架构 |

### 【底层原理（小白看这里）】

```
想象一个公司的门禁系统:

Access Token = 临时访客证（30分钟有效）
  - 进入每个房间都要刷这个卡
  - 过期了就不能用了
  - 被偷了最多损失30分钟

Refresh Token = 员工工牌（7天有效）
  - 不能直接开门！
  - 只能去前台（/api/v1/auth/refresh）换取新的访客证
  - 相当于"我还在职"的证明

三验证:
  1. 签名验证 = 检查卡片防伪标记（有没有被伪造？）
  2. 过期验证 = 检查有效期（过期了吗？）
  3. 黑名单验证 = 检查黑名单（被注销了吗？）
```

```
登录流程:
  用户 → POST /login → 返回 { token: "access...", refreshToken: "refresh..." }

正常请求:
  用户 → GET /api/xxx (Header: Bearer access_token)
       → Filter: 签名✓ 过期✓ 黑名单✓ 类型=access✓ → 放行

Access Token 过期:
  用户 → POST /refresh { refreshToken: "refresh..." }
       → 验证 refresh token → 返回新的 access token

注销:
  用户 → POST /logout (Header: Bearer access_token)
       → 将 access token 加入 Redis 黑名单
       → 前端清除两个 token
```

#### JwtUtil 核心改造

```java
// Token 生成 — 通过 tokenType claim 区分
private String buildToken(Long userId, String username, List<String> roles,
                          String tokenType, long expirationMs) {
    return Jwts.builder()
            .subject(username)
            .claim("userId", userId)
            .claim("roles", roles)
            .claim("tokenType", tokenType)  // "access" 或 "refresh"
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + expirationMs))
            .signWith(getSigningKey())
            .compact();
}

// 三验证
public Boolean validateToken(String token, String username) {
    extractUsername(token);       // 验证1: 签名（extractAllClaims 内部校验）
    if (isTokenExpired(token))    // 验证2: 过期
        return false;
    if (isTokenBlacklisted(token)) // 验证3: 黑名单（Redis）
        return false;
    return true;
}
```

#### Redis 黑名单实现

```java
// 黑名单 Key 格式: token:blacklist:{jwt_string}
// TTL = token 剩余有效时间（到期自动清除，避免 Redis 无限膨胀）

public void blacklistToken(String token) {
    Date expiration = extractExpiration(token);
    long ttlMs = expiration.getTime() - System.currentTimeMillis();
    if (ttlMs > 0) {
        stringRedisTemplate.opsForValue()
            .set("token:blacklist:" + token, "1", ttlMs, TimeUnit.MILLISECONDS);
    }
}
```

### 【常见疑问 (Q&A)】

**Q1: 前端怎么配合？**
> 1. 登录后保存 `token` 和 `refreshToken`
> 2. 每次请求在 Header 中携带 `Authorization: Bearer <access_token>`
> 3. 收到 401 时，调用 `/refresh` 接口用 refreshToken 换取新 accessToken
> 4. 如果 refreshToken 也过期，跳转到登录页

**Q2: Redis 挂了怎么办？**
> 黑名单检查失败时**放行**（`isTokenBlacklisted` 返回 false）。牺牲少量安全性换取可用性。短期内 access token 最多有效 30 分钟，风险可控。

**Q3: 为什么不用 Refresh Token Rotation（旋转刷新）？**
> Rotation 模式下每次刷新都会发新的 refresh token，旧的作废。这增加了复杂度，且需要处理并发刷新冲突。当前 7 天的 refresh token 已经足够安全，后续有需要可以升级。

**Q4: 旧版本 token（没有 tokenType 字段）还能用吗？**
> 兼容。`isTokenType()` 方法中，如果 token 没有 `tokenType` 字段，默认视为 `access` 类型。升级后旧 token 在过期前仍然有效。

## 4. 租户隔离方案分析

### 【痛点描述】

当前系统通过**分区（Partition）**实现了同一团队内的用户数据隔离，但**不同组织/企业之间没有数据隔离**：

```
现状：
  企业A 的用户 和 企业B 的用户 → 共享同一张 drones 表
  企业A 的管理员 → 理论上能看到企业B的无人机
```

### 【技术选型】

推荐 **共享表 + 行级过滤（Row-Level Security）** 方案：
- 在所有业务表添加 `tenant_id` 字段
- 利用 Hibernate Filter 自动在所有查询中注入 `WHERE tenant_id = ?`
- 通过 ThreadLocal（TenantContext）传播租户上下文

### 【底层原理（小白看这里）】

```
想象一个共享办公楼（数据库），每个公司（租户）租了一层:

  行级过滤 = 每个公司只能看到自己那层的房间（数据行）
  即使在同一张表里，tenant_id 不同就看不到

  SELECT * FROM drones WHERE tenant_id = 1;
  → 企业A 只能看到自己的无人机

  即使有人直接查所有数据:
  Hibernate Filter 会自动加上 WHERE tenant_id = 当前用户的租户ID
```

### 【当前状态】

**租户隔离未在当前阶段实现**，原因：
1. 改动面过大（涉及所有实体和查询）
2. 与 Kafka Phase 1 改造时间冲突
3. 需要数据迁移和前端配合

**详细实现方案见**：[Doc/租户隔离实现方案.md](./租户隔离实现方案.md)

该方案文档包含：
- 完整的数据库 Schema 变更 SQL
- 应用层改造代码示例（TenantContext、TenantFilter、Hibernate Filter）
- 分步实施路径（4个Phase，约6-8周）
- Kafka 消息租户隔离方案

### 【常见疑问 (Q&A)】

**Q1: 分区隔离和租户隔离有什么区别？**
> - **分区隔离（当前已有）**：控制"用户能看到哪些无人机的实时数据"，是功能级隔离
> - **租户隔离（待实现）**：控制"不同企业的数据完全不可见"，是安全级隔离
> - 两者正交：企业A内部仍然用分区管理用户权限

**Q2: 什么时候实现？**
> 建议在 Phase 2（微服务拆分）之后实现，此时每个微服务可独立改造，风险可控。

## 5. 下行命令 Epoch 校验

### 【痛点描述】

第 2 章介绍的 Epoch 机制只应用在**上行数据（遥测）**，但**下行数据（命令）**未经过 Epoch 过滤：

```
问题场景:
  t1: 用户发送 TAKEOFF 命令（epoch=1）
  t2: 无人机断电重启
  t3: 无人机重连（epoch=2）
  t4: TAKEOFF 命令才到达 Gateway（网络延迟）
  
  问题: Gateway 不检查 epoch，直接执行过时命令 → 无人机意外起飞！
```

还有一个类似问题：命令回执（commands.ack）也没有 Epoch 校验，导致前端可能收到过期的回执提示。

### 【技术选型】

复用已有的 Epoch 机制，将其扩展到下行链路：

| 链路 | 改造前 | 改造后 |
|------|---------|---------|
| 上行遥测 | ✅ 已有 Epoch | ✅ 保持 |
| 下行命令 | ❌ 无 Epoch | ✅ 发送时携带 + Gateway 消费时校验 |
| 命令回执 | ❌ 无 Epoch | ✅ Gateway 发送时携带 + 后端消费时校验 |

### 【底层原理（小白看这里）】

```
想象你给外卖小哥打电话说"送到A地址"（命令）。

但你已经搬家了（无人机重启），新地址是 B。

如果外卖小哥不检查你的"地址版本号"(epoch)，
就会把餐送到旧地址A → 卖家收不到！

改造后：每个命令都携带 epoch，
外卖小哥发现 epoch 不匹配就丢弃旧命令 → 安全！
```

```
                        命令下发流程（改造后）
                        
  Backend                    Kafka                    Gateway
  │                          │                        │
  │ sendCommand()            │                        │
  │ + epoch=2               │                        │
  │ ────────────────────→  │  commands.down          │
  │                          │ ───────────────────→  │
  │                          │                        │ 检查: msgEpoch(2)
  │                          │                        │       >= currentEpoch(2)
  │                          │                        │ → 执行命令 ✓
  │                          │                        │
  │ 旧命令(epoch=1)         │                        │
  │ ────────────────────→  │  commands.down          │
  │                          │ ───────────────────→  │
  │                          │                        │ 检查: msgEpoch(1)
  │                          │                        │       < currentEpoch(2)
  │                          │                        │ → 丢弃！ ✗
```

### 【实现细节】

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| 命令发送 | `kafka/CommandKafkaProducer.java` | `sendCommand()` 中添加 `epoch` 字段 |
| Gateway 校验 | `dds-gateway/dds_gateway.py` | `_start_kafka_command_consumer()` 中校验 epoch + 时间戳 |
| 回执校验 | `kafka/CommandKafkaConsumer.java` | `consumeCommandAck()` 中校验 epoch |
| 回执携带 epoch | `dds-gateway/dds_gateway.py` | `_on_vehicle_command_ack()` 中添加 epoch 字段 |

#### 命令消息格式（改造后）

```json
// commands.down 消息
{
  "uavId": "px4_1",
  "commandType": "TAKEOFF",
  "params": "{}",
  "timestamp": "2024-01-01T00:00:00Z",
  "userId": 1,
  "commandLogId": 123,
  "epoch": 3
}

// commands.ack 消息
{
  "uavId": "px4_1",
  "command": 400,
  "result": 0,
  "timestamp": 1704067200.0,
  "epoch": 3
}
```

#### Gateway 端双重校验

Gateway 消费命令时同时检查：
1. **Epoch 校验**：`msgEpoch < currentEpoch` → 丢弃（过时代际）
2. **时间戳校验**：命令年龄 > 60秒 → 丢弃（超时命令）

### 【常见疑问 (Q&A)】

**Q1: 为什么命令还需要时间戳校验，Epoch 不够吗？**
> Epoch 防的是"重启后的旧命令"，时间戳防的是"网络严重延迟的命令"。两者互补，双保险。

**Q2: 旧版本 Gateway 不支持 epoch 字段怎么办？**
> `data.get('epoch', 0)` 默认值为 0，当 `currentEpoch=0` 时 `0 < 0` 为 false，不会被过滤。向后兼容。

## 6. Epoch 定期重置机制

### 【痛点描述】

Epoch 值只增不减，长期运行后可能出现问题：

```
场景: 某架无人机每天重连 10 次，运行 3 年后:
  epoch = 10 × 365 × 3 = 10,950

问题 1: 内存占用——即使无人机已下线半年，epoch 记录仍占用内存
问题 2: 数值增长——虽然不会溢出(Long)，但数值越来越大不美观，也不利于监控
问题 3: 消息体积——epoch 值较大时占用更多字节（微小影响，但千万级时累积明显）
```

### 【技术选型】

**定期维护策略**：后端 + Gateway 双端同时执行维护任务。

| 策略 | 触发条件 | 操作 |
|------|----------|------|
| 归一化 | epoch > 10,000 | 重置为 1 |
| 超时清除 | 无人机超过 24 小时未活跃 | 移除 epoch 记录 |
| 执行频率 | 每 6 小时 | 自动执行 |

### 【底层原理（小白看这里）】

```
想象你家门牌号码每次换钥匙就 +1：
  第1把钥匙: 门牌=1
  第2把钥匙: 门牌=2
  ...
  第10001把钥匙: 门牌=10001 → 号码太大了！

定期重置就像物业每年重新编号：
  10001 → 重置为 1
  下次换钥匙变成 2，不会与旧的 10001 混淆。

超时清除就像物业清理已搬走住户的信箱：
  如果你半年没收信，信箱就被回收了。
```

### 【实现细节】

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| 后端定期维护 | `kafka/EpochManager.java` | `periodicEpochMaintenance()` 方法，`@Scheduled(fixedRate=6h)` |
| Gateway定期维护 | `dds-gateway/dds_gateway.py` | `_start_epoch_maintenance()` 后台线程 |

#### 后端 EpochManager 维护逻辑

```java
// EpochManager.java
@Scheduled(fixedRate = 6 * 60 * 60 * 1000) // 每 6 小时
public void periodicEpochMaintenance() {
    for (Map.Entry<String, Long> entry : epochMap.entrySet()) {
        String uavId = entry.getKey();
        long epoch = entry.getValue();
        long idleMs = now - lastUpdateMap.getOrDefault(uavId, 0L);
        
        if (idleMs > 24小时) {
            epochMap.remove(uavId);      // 超时清除
        } else if (epoch > 10000) {
            epochMap.put(uavId, 1L);     // 归一化
        }
    }
}
```

#### Gateway 端维护逻辑

```python
# dds_gateway.py - _start_epoch_maintenance()
def _maintenance_loop():
    while self.running:
        time.sleep(6 * 3600)  # 每 6 小时
        for uav_id in list(self._epoch_map.keys()):
            state = self.drone_states.get(uav_id)
            idle_s = time.time() - state.last_update
            
            if idle_s > 24 * 3600:
                self._epoch_map.pop(uav_id)  # 超时清除
            elif self._epoch_map[uav_id] > 10000:
                self._epoch_map[uav_id] = 1  # 归一化
```

### 【常见疑问 (Q&A)】

**Q1: 归一化后会不会导致正常消息被丢弃？**
> 不会。归一化后 epoch=1，下次无人机发送的新消息 epoch >= 1，`validateEpoch()` 使用 `>=` 比较，一定接受。

**Q2: 后端和 Gateway 的重置会不会冲突？**
> 不会。两端独立维护各自的 epoch 记录。后端重置后接受 Gateway 发来的任何 >= 1 的 epoch，Gateway 重置后同理。

## 7. 网关健康监控与断电检测

### 【痛点描述】

网关断电后，前端完全无感知：

```
场景: 网关机房突然断电

  t0: 无人机正常飞行，前端显示"在线"
  t1: 网关断电，停止发送遥测
  t2: Redis 中 drone:px4_1:online 键过期（TTL=30s）
  t3: 前端仍然显示最后已知状态（"在飞"）
  t4: 用户并不知道无人机已失联 10 分钟...
  
  风险: 无人机可能电量耗尽坠毁，用户却以为一切正常
```

### 【技术选型】

**基于 Redis 心跳 TTL 的被动检测方案**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| Gateway 主动报心跳 | 实时性高 | 网关断电后不会发心跳，就是检测不到 |
| **后端定时扫描 Redis** | **利用已有心跳 TTL，零改动 Gateway** | 延迟 60s |
| 前端定时轮询 | 简单 | 浪费带宽，延迟更高 |

选择方案 2：后端扫描 Redis。原因：
1. **零改动 Gateway**：利用已有的 `drone:{uavId}:online` TTL 机制
2. **自动检测**：网关断电 → 停止发遥测 → Redis TTL 过期 → 后端发现无在线无人机
3. **60 秒阻尼**：避免网络抖动导致的误报

### 【底层原理（小白看这里）】

```
想象你是保安，每 10 秒巡逻一次大楼。

每个办公室门口有一盏灯（Redis TTL=30s）。
只要里面有人办公，灯就亮着。
人走了（无人机断联），30秒后灯自动灭。

保安巡逻时检查:
  - 有灯亮 → 正常，继续巡逻
  - 所有灯都灭了 → 记一笔
  - 连续 6 次巡逻(60s)所有灯都灭 → 报警: "可能停电了!"
  - 突然又有灯亮了 → 取消报警: "恢复了!"
```

```
           网关健康监控流程

  Redis                     GatewayHealthMonitor          Frontend
  │                           │                            │
  │  drone:px4_1:online       │                            │
  │  TTL=30s                  │                            │
  │                           │ 每10s检查                   │
  │ ←───────────────────────  │ keys("drone:*:online")     │
  │ ───── px4_1 ──────────→  │                            │
  │                           │ 有在线无人机 → 正常         │
  │                           │                            │
  │  [网关断电]               │                            │
  │  TTL过期, key消失         │                            │
  │                           │ 检查: 0个在线 (1/6)        │
  │                           │ 检查: 0个在线 (2/6)        │
  │                           │ ...                        │
  │                           │ 检查: 0个在线 (6/6)        │
  │                           │ ─── GATEWAY_OFFLINE ─────→ │
  │                           │                            │ 显示警告
  │                           │                            │ 标记离线
```

### 【实现细节】

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| 健康监控器 | `kafka/GatewayHealthMonitor.java` | `@Scheduled(fixedRate=10s)` 定时检查 |
| Redis 查询 | `service/RedisService.java` | `getAllOnlineDroneIds()` 扫描 drone:*:online |
| 离线广播 | `service/WebSocketGatewayService.java` | `broadcastOfflineStatus()` WebSocket 推送 |

#### 前端 WebSocket 监听示例

```javascript
// 前端监听新增的 /topic/drone-status 主题
stompClient.subscribe('/topic/drone-status', function(message) {
    var data = JSON.parse(message.body);
    
    if (data.type === 'gateway_offline') {
        // 显示警告: "网关失联，无人机数据不可用"
        showAlert('⚠️ 网关离线', data.reason);
        // 将所有无人机标记为离线
        data.offlineDrones.forEach(id => markDroneOffline(id));
    }
    
    if (data.type === 'gateway_recovered') {
        // 取消警告
        clearAlert();
        // 等待遥测数据自动恢复
    }
});
```

#### 监控参数

| 参数 | 值 | 说明 |
|------|------|------|
| 检查频率 | 10 秒 | 平衡响应速度和 Redis 负载 |
| 离线阈值 | 60 秒 (6 次检查) | 避免网络抖动导致的误报 |
| 心跳 TTL | 30 秒 | 无人机 30 秒无数据则认为断联 |

### 【常见疑问 (Q&A)】

**Q1: 为什么要等 60 秒才报警，不能更快吗？**
> 抖动保护。网络瞬断、Gateway GC 停顿、Redis 短暂不可用都可能导致短暂无心跳。如果立即报警会产生大量误报。可根据实际需要调整 `OFFLINE_THRESHOLD` 值。

**Q2: 多实例后端会重复报警吗？**
> 当前单实例不会（`gatewayOfflineAlerted` 标志位防止重复）。多实例部署时，可通过 Redis 分布式锁确保只有一个实例发送报警（Phase 2 优化项）。

**Q3: 前端如果没有监听 /topic/drone-status 会怎样？**
> 不会报错，只是前端不会收到离线通知。前端需要添加监听代码（见上方示例）。这是一个可选的前端增强，后端已就绪。

## 8. 微服务拆分（多模块Maven工程）

### 【痛点描述】

原系统是一个**单体 Spring Boot 应用**，所有功能（遥测接入、数据存储、实时推送、指令下发、用户管理）打包在一个 JAR 中：

```
backend/
├── controller/    ← 所有 REST 接口（20+ Controller）
├── service/       ← 所有业务逻辑
├── kafka/         ← Kafka 消费者/生产者
└── security/      ← JWT 鉴权
```

**三个核心问题：**

| # | 问题 | 严重程度 | 具体表现 |
|---|------|----------|----------|
| 1 | 无法独立扩缩 | 高 | 遥测接入需要 16 实例，但用户管理只需 2 实例，单体只能整体扩容，浪费资源 |
| 2 | 故障传播 | 高 | 数据库慢查询拖慢整个应用，WebSocket 推送也受影响 |
| 3 | 部署耦合 | 中 | 修改用户管理代码需要重新部署整个系统，影响实时遥测 |

### 【技术选型】

**Maven 多模块 + Spring Boot 独立部署**

| 方案 | 优点 | 缺点 | 适合场景 |
|------|------|------|----------|
| **Maven 多模块** | 共享代码、统一版本、IDE友好 | 需要规划模块边界 | **中等规模微服务** |
| Spring Cloud 全家桶 | 服务发现、配置中心 | 重量级、学习曲线陡 | 大型企业应用 |
| 独立仓库 | 完全解耦 | 共享代码困难 | 超大型团队 |

### 【底层原理（小白看这里）】

```
想象一个餐厅（单体应用）：
  一个厨师同时做前菜、主菜、甜点、饮料。
  客人多的时候，所有菜都变慢。

微服务拆分后：
  前菜站（ucs-telemetry-ingest）—— 专门接收遥测数据
  主菜站（ucs-telemetry-store）—— 专门存储数据
  饮料站（ucs-realtime-push） —— 专门推送实时数据
  收银台（ucs-api-gateway）   —— 统一入口，分配请求

  前菜站忙的时候，多开几个窗口（水平扩容），不影响其他站。
```

```
ucs-platform/                    ← Maven 父 POM
├── ucs-common/                  ← 共享模块（DTO、工具类、公共服务）
├── ucs-api-gateway/             ← 统一网关（端口 8080）

## 9. TimescaleDB 时序存储引入

### 【痛点描述】

原系统使用普通 PostgreSQL 存储遥测数据：

```sql
-- 改造前：普通表，随数据量增长查询越来越慢
INSERT INTO telemetry_data (uav_id, lat, lon, alt, ...) VALUES (...);
SELECT * FROM telemetry_data WHERE uav_id = 'px4_1' ORDER BY created_at DESC;
-- 1000万条记录后：查询 > 5秒
```

**核心问题：**

| # | 问题 | 说明 |
|---|------|------|
| 1 | 写入瓶颈 | 单表写入 < 5000 rows/s，千万级无人机需要 > 50000 rows/s |
| 2 | 查询性能退化 | 数据量增长后，时间范围查询急剧变慢 |
| 3 | 存储膨胀 | 无自动压缩/过期清理，磁盘快速耗尽 |

### 【技术选型】

**TimescaleDB** — PostgreSQL 的时序数据扩展。

| 方案 | 写入吞吐 | SQL兼容 | 自动压缩 | 学习成本 |
|------|----------|---------|----------|----------|
| **TimescaleDB** | **>50k rows/s** | **完全兼容PostgreSQL** | **有** | **低（就是PG）** |
| InfluxDB | 100k rows/s | 不兼容 | 有 | 中 |
| ClickHouse | 500k rows/s | 部分兼容 | 有 | 高 |
| 普通PostgreSQL | <5k rows/s | 完全兼容 | 无 | 无 |

**选择 TimescaleDB 的原因：**
1. 完全兼容 PostgreSQL — 现有 SQL/JDBC 代码零改造
2. Hypertable 自动分片 — 按时间分 chunk，写入和查询都快
3. 内置压缩+保留策略 — 自动管理数据生命周期

### 【底层原理（小白看这里）】

```
想象一个巨大的文件柜（普通 PostgreSQL 表）：
  所有遥测数据塞在一个抽屉里。
  找最近 1 小时的数据？要翻遍整个抽屉。

TimescaleDB 的 Hypertable：
  自动按时间切成小抽屉（Chunk），每个抽屉 = 1小时数据。
  找最近 1 小时？只翻最后 1 个抽屉就行！

  ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ 10:00-11 │ │ 11:00-12 │ │ 12:00-13 │  ← 每个 Chunk = 1小时
  │ 5万条    │ │ 5万条    │ │ 3万条    │
  └──────────┘ └──────────┘ └──────────┘
       ↓              ↓
    2小时后自动压缩   当前写入中
    （节省90%空间）   
```

### 【实现细节】

#### 初始化脚本

位置：`ucs-platform/ucs-telemetry-store/src/main/resources/db/migration/V1__timescaledb_init.sql`

```sql
-- 1. 创建 hypertable（chunk_interval = 1小时）
SELECT create_hypertable('telemetry_data', 'time', chunk_time_interval => INTERVAL '1 hour');

-- 2. 压缩策略（2小时以上自动压缩）
SELECT add_compression_policy('telemetry_data', INTERVAL '2 hours');

-- 3. 保留策略（7天以上自动删除）
SELECT add_retention_policy('telemetry_data', INTERVAL '7 days');

-- 4. 连续聚合（1分钟粒度汇总，用于报表）
CREATE MATERIALIZED VIEW telemetry_1min WITH (timescaledb.continuous) AS
SELECT time_bucket('1 minute', time) AS bucket, uav_id,
       AVG(speed) AS avg_speed, MIN(battery) AS min_battery, ...
FROM telemetry_data GROUP BY bucket, uav_id;
```

#### 批量写入（Kafka 批量消费 → JDBC batchUpdate）

```
Kafka telemetry.raw ──batch(500条)──→ TelemetryBatchConsumer ──batchUpdate──→ TimescaleDB
                                      ↑
                               fetch-min-size: 64KB
                               max-poll-records: 500
```

位置：`ucs-platform/ucs-telemetry-store/src/main/java/com/ucs/store/consumer/TelemetryBatchConsumer.java`

#### Docker 启动

```bash
# TimescaleDB 在 docker-compose-microservices.yml 中自动启动
# 端口 5433（避免与业务 PostgreSQL 的 5432 冲突）
docker-compose -f docker-compose-microservices.yml up timescaledb -d
```

### 【常见疑问 (Q&A)】

**Q1: TimescaleDB 和普通 PostgreSQL 可以混用吗？**
> 可以。TimescaleDB 只是 PG 的扩展插件。业务数据用普通 PG 表（端口5432），遥测数据用 TimescaleDB hypertable（端口5433），互不影响。

**Q2: 7天保留策略会丢数据吗？**
> 原始数据7天后自动删除，但连续聚合视图 `telemetry_1min` 保留1分钟粒度的汇总数据，可用于历史报表。如需长期保留原始数据，调整 retention_policy 即可。

## 10. Redis Cluster 集群升级

### 【痛点描述】

原系统使用**单实例 Redis**：

```properties
# 改造前
spring.data.redis.host=localhost
spring.data.redis.port=6379
```

**核心问题：**

| # | 问题 | 说明 |
|---|------|------|
| 1 | 单点故障 | Redis挂了，所有依赖Redis的服务不可用（在线状态、分区缓存、JWT黑名单） |
| 2 | 内存上限 | 单机最大内存有限，千万级无人机状态无法全部缓存 |
| 3 | 无法水平扩展 | 单实例的QPS有天花板 |

### 【技术选型】

**Redis Cluster（官方集群方案）**

| 方案 | 高可用 | 水平扩展 | 复杂度 |
|------|--------|----------|--------|
| **Redis Cluster** | **自动故障转移** | **哈希槽分片** | **中** |
| Redis Sentinel | 主从切换 | 不支持 | 低 |
| Codis/Twemproxy | 依赖代理 | 代理分片 | 高 |

### 【底层原理（小白看这里）】

```
想象一个图书馆（Redis），只有 1 个管理员（单实例）：
  管理员请假 → 整个图书馆关门。
  书太多 → 一个管理员忙不过来。

Redis Cluster（6个管理员，3主3从）：
  主管理员 A 负责 0-5460 号书架    ← Master 1
  主管理员 B 负责 5461-10922 号书架 ← Master 2
  主管理员 C 负责 10923-16383 号书架 ← Master 3
  
  每个主管理员有一个副手（Slave），主管理员请假时副手顶上。
  
  drone:px4_1:state → hash("drone:px4_1:state") % 16384 = 8888
  → 8888 在 B 的范围内 → 交给 Master 2 处理
```

### 【实现细节】

#### Docker 启动 6 节点集群

```bash
docker-compose -f docker-compose-redis-cluster.yml up -d
# 等待 redis-cluster-init 自动完成集群组建
```

#### 应用配置

```yaml
# 各微服务 application.yml
spring:
  data:
    redis:
      cluster:
        nodes: localhost:6371,localhost:6372,localhost:6373,localhost:6374,localhost:6375,localhost:6376
      lettuce:
        pool:
          max-active: 32
          max-idle: 16
```

#### Lettuce 客户端（自动集群感知）

Spring Boot Starter Data Redis 默认使用 Lettuce 客户端，自动支持 Cluster 模式：
- 自动发现所有节点
- 自动路由到正确的哈希槽
- 自动故障转移（Master 挂了切换到 Slave）

#### 关键代码位置

| 组件 | 文件 | 说明 |
|------|------|------|
| Redis键常量 | `ucs-common/.../config/RedisKeyConstants.java` | 统一键命名（drone:{uavId}:state 等） |
| Redis集群服务 | `ucs-common/.../service/RedisClusterService.java` | 无人机状态CRUD、分区路由、在线心跳 |
| 集群配置 | `docker-compose-redis-cluster.yml` | 6节点集群+自动初始化 |

### 【常见疑问 (Q&A)】

**Q1: 本地开发必须启动 6 节点吗？**
> 不需要。各微服务配置了 fallback：如果 `REDIS_CLUSTER_NODES` 环境变量未设置，会降级到单节点模式 `localhost:6379`。开发时直接用单 Redis 即可。

**Q2: Cluster 模式下 Redis GEO 命令能用吗？**
> 能用。`GEOADD drone:positions lon lat uavId` 中 `drone:positions` 是单个 key，所有 GEO 操作落在同一个哈希槽。注意不要用 `{tag}` 语法把不同 key 强制分到同一个槽（除非有跨 key 事务需求）。

## 11. Spring Cloud Gateway 统一网关

### 【痛点描述】

微服务拆分后，前端需要知道每个服务的地址和端口：

```
前端 → http://localhost:8081/api/telemetry  （遥测）
     → http://localhost:8084/api/commands   （指令）
     → http://localhost:8086/api/users      （用户）
     → ws://localhost:8083/ws              （WebSocket）

问题：前端需要维护多个地址，跨域配置分散在每个服务中。

### 【技术选型】

**Spring Cloud Gateway** — 基于 WebFlux 的 API 网关。

| 方案 | 性能 | Spring生态 | 灵活性 |
|------|------|------------|--------|
| **Spring Cloud Gateway** | **高（非阻塞）** | **原生集成** | **高** |
| Nginx | 极高 | 需要额外配置 | 中 |
| Kong | 高 | 需要适配器 | 高 |

### 【底层原理（小白看这里）】

想象一个酒店前台（Gateway）：

## 12. 视口裁剪与降采样推送

### 【痛点描述】

原系统将**所有在线无人机的遥测数据**推送给**每一个**前端客户端：

```
10万架在线无人机 × 10Hz 推送频率 × 50 个客户端 = 5000万条/秒 推送量
问题：大部分数据对用户无意义（用户只看地图上可见的区域）
```

### 【技术选型】

**视口裁剪 + 缩放级别降采样**

| 策略 | 说明 | 效果 |
|------|------|------|
| 视口裁剪 | 只推送地图可见区域内的无人机 | 减少 80-95% 数据量 |
| 降采样 | 缩放级别低时降低推送频率 | 再减少 50-90% |

### 【底层原理（小白看这里）】

```
想象你用手机看一张超大地图（如全国无人机分布）：
  手机屏幕只能显示一小块区域（视口）。
  屏幕外的无人机数据传到你手机上也没用。

视口裁剪：
  ┌─── 全国 ─────────────────────────┐
  │                                   │
  │     ┌── 视口 ──┐                  │
  │     │ ●  ●     │  只推送这3架     │
  │     │      ●   │                  │
  │     └──────────┘                  │
  │  ●                ● ← 这些不推送   │
  │        ●      ●                   │
  └───────────────────────────────────┘

降采样：
  zoom >= 15（很近，看到每架无人机）：10Hz 全速推送
  zoom 10-14（中等距离）：2Hz
  zoom < 10（全国概览）：0.5Hz（2秒一次足够）
```

### 【实现细节】

#### 前端：监听地图移动，发送视口边界

位置：`frontend/ucs-dashboard/src/hooks/useViewportClipping.ts`

```typescript
// 地图移动结束时，发送视口信息到后端
map.on('moveend', () => {
  const bounds = map.getBounds();
  stompClient.publish({
    destination: '/app/viewport/update',
    body: JSON.stringify({
      minLat: bounds.getSouthWest().lat,
      maxLat: bounds.getNorthEast().lat,
      minLon: bounds.getSouthWest().lng,
      maxLon: bounds.getNorthEast().lng,
      zoomLevel: Math.round(map.getZoom())
    })
  });
});
```

#### 后端：接收视口更新，过滤推送

位置：`ucs-platform/ucs-realtime-push/src/main/java/com/ucs/push/websocket/ViewportController.java`

```
前端 moveend → /app/viewport/update → ViewportController
                                          ↓
                                    更新 session 视口缓存
                                          ↓
                                    查询 GeoHash 索引
                                          ↓
                                    返回视口内无人机列表
```

#### 降采样逻辑

位置：`ucs-common/src/.../service/ViewportFilterService.java`

```java
public static long getPushIntervalMs(int zoomLevel) {
    if (zoomLevel >= 15) return 100;   // 10Hz
    if (zoomLevel >= 10) return 500;   // 2Hz
    return 2000;                        // 0.5Hz
}
```

### 【常见疑问 (Q&A)】

**Q1: 视口更新频率会不会太高？**
> useViewportClipping 内置 300ms 防抖（debounce），地图拖动结束后 300ms 才发送一次视口更新。

**Q2: 未设置视口的客户端怎么处理？**
> 如果客户端未发送视口信息，默认接收所有无人机数据（兼容旧客户端）。

## 13. GeoHash 空间索引

### 【痛点描述】

视口裁剪需要快速查询「哪些无人机在这个矩形区域内」：

```
暴力方法：遍历所有在线无人机，逐个检查 lat/lon 是否在视口内
  10万架在线 × 每秒 50 次视口查询 = 500万次比较/秒
  延迟: > 100ms → 用户体验差
```

### 【技术选型】

**Redis GEO + GeoHash 反向索引**

| 方案 | 查询延迟 | 内存占用 | 实现复杂度 |
|------|----------|----------|------------|
| 暴力遍历 | > 100ms | 低 | 低 |
| R-Tree | < 10ms | 中 | 高（需要自己实现） |
| **GeoHash + Redis GEO** | **< 10ms** | **< 2GB/千万** | **低（Redis原生支持）** |
| PostGIS | < 20ms | 高 | 中 |

### 【底层原理（小白看这里）】

```
GeoHash 原理：把地球表面切成网格，每个网格有一个编码。

精度 6（~1.2km × 0.6km）：
  ┌──────┬──────┬──────┐
  │wx4g0s│wx4g0t│wx4g0u│
  ├──────┼──────┼──────┤
  │wx4g0e│wx4g0f│wx4g0g│  ← 每个格子 ~1.2km×0.6km
  ├──────┼──────┼──────┤
  │wx4g0d│wx4g0c│wx4g0b│
  └──────┴──────┴──────┘

无人机位置 (30.5, 104.1) → GeoHash = "wx4g0f"

查询视口内的无人机：
  1. 计算视口覆盖哪些 GeoHash 格子 → {wx4g0e, wx4g0f, wx4g0g}
  2. 查 Redis: SMEMBERS geohash:wx4g0e → {px4_1, px4_3}
  3. 查 Redis: SMEMBERS geohash:wx4g0f → {px4_2}
  4. 合并 → {px4_1, px4_2, px4_3}

查询时间 = O(k)，k = GeoHash格子数量（通常 < 100）
不管有多少架无人机，查询时间几乎不变！
```

### 【实现细节】

#### GeoHash 编码工具

位置：`ucs-common/src/.../util/GeoHashUtil.java`

```java
// 编码：经纬度 → GeoHash 字符串
GeoHashUtil.encode(30.5, 104.1)  // → "wx4g0f"

// 覆盖：视口边界 → 所有覆盖的 GeoHash 格子
GeoHashUtil.coverBoundingBox(minLat, maxLat, minLon, maxLon)
// → {"wx4g0e", "wx4g0f", "wx4g0g", ...}
```

#### Redis 双索引

位置：`ucs-common/src/.../service/GeoSpatialService.java`

```java
// 1. Redis GEO 命令（精确距离查询）
redisTemplate.opsForGeo().add("drone:positions", new Point(lon, lat), uavId);

// 2. GeoHash 反向索引（视口查询）
redisTemplate.opsForSet().add("geohash:wx4g0f", uavId);
```

#### 索引更新时机

```
遥测消息到达 → TelemetryRawConsumer (ucs-telemetry-ingest)
  → 更新 Redis 状态 (drone:{uavId}:state)
  → 更新心跳 (drone:{uavId}:online)
  → 更新 GeoHash 索引 (GEOADD + SADD)  ← 在这里更新
```

#### REST API 查询

```
GET /api/v1/drones/viewport?minLat=30&maxLat=31&minLon=104&maxLon=105
→ GeoHash覆盖 → Redis SMEMBERS → 返回无人机ID列表

GET /api/v1/drones/nearby?lat=30.5&lon=104.1&radiusKm=10
→ Redis GEORADIUS → 返回附近无人机
```

### 【常见疑问 (Q&A)】

**Q1: GeoHash 精度为什么选 6？**
> 精度 6 对应 ~1.2km × 0.6km 的网格。对于无人机视口查询，这个粒度提供了良好的平衡：网格不会太大（避免返回过多无关无人机），也不会太小（避免过多 Redis 查询）。

**Q2: 无人机移动后旧 GeoHash 怎么清理？**
> 当前实现在 `updateDronePosition()` 中先写入新位置的 GeoHash，旧 GeoHash 中的 uavId 会在下次清理时移除。优化方向：记录上次 GeoHash，移动后先 SREM 旧的再 SADD 新的。

**Q3: 千万级无人机内存够吗？**
> 估算：每架无人机占 ~200 bytes（GEO + GeoHash Set），千万架 ≈ 2GB。Redis Cluster 3 主节点平均每节点 ~700MB，在 512MB maxmemory 配置下可能需要调高。生产建议 4GB/节点。
