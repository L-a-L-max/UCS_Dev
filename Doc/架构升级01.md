## 一、当前架构问题诊断

### 1.1 核心问题汇总（源码级证据）

| 问题 | 代码位置 | 影响 | 严重程度 |
|------|---------|------|---------|
| **DDS 组播限制** | `dds_gateway.py:164-174` | 无法跨公网，限制局域网部署 | ⚠️ **架构性阻碍** |
| **单点故障链** | 所有组件单实例 | 任一组件宕机→全系统不可用 | 🔴 **高** |
| **消息乱序** | `DDSGatewayController.java:67-148` | HTTP无序号，多实例乱序 | 🔴 **高** |
| **过期消息** | `DroneState` 无epoch字段 | 断电重连消费旧数据 | 🔴 **高** |
| **事件流混合** | `DDSGatewayController.java:93-122` | armed变化被遥测延迟 | 🟡 **中** |
| **持久化瓶颈** | `TelemetryPersistenceService.java:33` | 无界队列OOM，JPA慢 | 🔴 **高** |
| **WebSocket不可扩展** | `WebSocketConfig.java` SimpleBroker | 单实例5000连接上限 | 🔴 **高** |
| **热路径DB写入** | `PartitionRoutingService.java:182` | 新无人机触发DB写入 | 🟡 **中** |

**瓶颈量化**：

```
当前能力 vs 千万级需求:
- DDS Gateway:    100架/s      vs  1亿msg/s     → 100万倍差距
- HTTP转发:       200 req/s    vs  百万批次/s   → 5000倍差距
- PostgreSQL写入: 1000条/5s    vs  100万条/s    → 5000倍差距
- WebSocket:      5000连接     vs  千万级推送   → 无法扩展
```

### 1.2 当前数据流

```
遥测流（上行）:
PX4 ──DDS/ROS2(UDP组播, 仅局域网)──► dds_gateway.py (单Python进程, spin_once单线程)
                                        │
                                        │ HTTP POST /api/v1/dds-gateway/telemetry
                                        │ (同步, 批量, ~1秒/次)

                              Spring Boot Backend (单实例, 8080端口)

                               ├── WebSocketGatewayService  → SimpleBroker广播STOMP
                               └── RedisService             → drone:{uavId}:online 30s TTL
                                        │
                                        │ STOMP WebSocket /topic/telemetry/partition/{name}
                                        ▼
                              React Frontend (Vite + MapLibre)

命令流（下行）:
Frontend ──HTTP──► ControlService ──HTTP POST:5050──► dds_gateway.py ──DDS──► PX4
```

## 二、Zenoh 迁移对架构的影响

### 2.1 为什么必须迁移到 Zenoh

**DDS 的根本限制**：

| 问题 | DDS 现状 | Zenoh 解决方案 |
|------|---------|--------------|
| **组播依赖** | 基于UDP组播，无法跨路由器/NAT | 支持TCP/QUIC/TLS，天然穿越NAT |
| **公网传输** | 无法跨公网，需要VPN隧道 | 原生支持WAN路由，无需VPN |
| **发现开销** | 组播发现流量随节点数量平方增长 | 集中式路由器发现，O(1)开销 |
| **跨域通信** | ROS_DOMAIN_ID隔离，跨域需要Bridge | 统一key-space，天然跨域 |
| **嵌入式支持** | 资源消耗大，不适合MCU | Zenoh-Pico最小300字节，支持MCU |
| **性能** | UDP组播在局域网快，WAN场景差 | 比DDS快2倍，比Kafka快50倍 |

**性能对比**（来源：NTU研究论文，2023）：

| 协议 | 单机吞吐量 | 多机吞吐量 | 延迟 |
|------|----------|----------|------|
| DDS (CycloneDDS) | ~30 Gbps | ~25 Gbps | 最低（局域网UDP） |
| **Zenoh** | **67 Gbps** | **51 Gbps** | 低（WAN场景优于DDS） |
| MQTT | ~1 Gbps | ~1 Gbps | 中 |
| Kafka | ~1.3 Gbps | ~1 Gbps | 高 |

### 2.2 Zenoh Java 支持的架构优化机会

**关键发现**：Zenoh 对 Java 的良好支持（zenoh-java 1.4.0）使得我们可以**消除 Python Gateway 层**，直接在 Spring Boot 中集成 Zenoh 订阅。

#### 当前架构（Python Gateway 中转）

```
PX4 ──DDS──► Python dds_gateway.py ──HTTP──► Spring Boot Backend
             (1492行Python代码)              (DDSGatewayController.java)
             - rclpy订阅
             - 单线程spin_once()
             - 同步HTTP POST
```

**问题**：
- Python ↔ Java 跨语言通信开销
- HTTP 同步调用延迟
- Python GIL 限制多核利用
- 两层技术栈运维复杂

#### 优化后架构（Zenoh Java 直接集成）

```
PX4 ──Zenoh-Pico──► Zenoh Router ──► Spring Boot Gateway Service (Java)
                                     (使用 zenoh-java SDK)
                                     - 多线程Zenoh订阅
                                     - 直接写入Kafka
                                     - 无HTTP中转
```

**优势**：
1. **消除跨语言边界**：Java → Java，无序列化开销
2. **统一技术栈**：全Java生态，简化运维
3. **多线程并发**：Java线程池 vs Python GIL
4. **直接Kafka集成**：Spring Kafka 深度集成，无需HTTP中转
5. **更好的可观测性**：Spring Boot Actuator + Micrometer 统一监控

### 2.3 Zenoh Java 集成示例

**Maven 依赖**：

```xml
<dependency>
    <groupId>org.eclipse.zenoh</groupId>
    <artifactId>zenoh-java</artifactId>
    <version>1.4.0</version>
</dependency>
```

**Spring Boot Gateway Service 核心代码**：

```java
@Service
@Slf4j
public class ZenohGatewayService {
    
    private final KafkaTemplate<String, String> kafkaTemplate;
    private Session zenohSession;
    private final Map<String, Subscriber> subscribers = new ConcurrentHashMap<>();
    
    @PostConstruct
    public void initZenoh() throws ZenohException {
        // 连接Zenoh Router
        Config config = Config.loadFromFile("zenoh-config.json5");
        this.zenohSession = Zenoh.open(config);
        log.info("Zenoh session opened, connected to router");
    }
    
    /**
     * 订阅指定无人机的遥测话题
     */
    public void subscribeDrone(String uavId) {
        String keyExpr = uavId + "/fmu/out/**";  // 订阅所有输出话题
        
        Subscriber subscriber = zenohSession.declareSubscriber(
            keyExpr,
            sample -> {
                // 解析Zenoh消息
                String topic = sample.getKeyExpr().toString();
                byte[] payload = sample.getPayload();
                
                // 根据话题类型解析（使用CDR反序列化）
                if (topic.contains("vehicle_global_position")) {
                    handleGlobalPosition(uavId, payload);
                } else if (topic.contains("vehicle_status")) {
                    handleVehicleStatus(uavId, payload);
                }
                // ... 其他话题
            }
        );
        
        subscribers.put(uavId, subscriber);
        log.info("Subscribed to Zenoh topics for drone: {}", uavId);
    }
    
    private void handleGlobalPosition(String uavId, byte[] payload) {
        // CDR反序列化（使用CycloneDDS CDRSTREAM库）
        VehicleGlobalPosition msg = CdrDeserializer.deserialize(
            payload, VehicleGlobalPosition.class);
        
        // 构建遥测消息
        TelemetryMessage telemetry = TelemetryMessage.builder()
            .uavId(uavId)
            .lat(msg.getLat())
            .lon(msg.getLon())
            .alt(msg.getAlt())
            .timestamp(Instant.now())
            .epoch(getCurrentEpoch(uavId))  // 代际ID
            .build();
        
        // 直接写入Kafka（按uav_id分区，保证有序）
        kafkaTemplate.send("telemetry.raw", uavId, toJson(telemetry));
    }
    
    /**
     * 发送命令到PX4
     */
    public void sendCommand(String uavId, VehicleCommand cmd) {
        String keyExpr = uavId + "/fmu/in/vehicle_command";
        byte[] payload = CdrSerializer.serialize(cmd);
        
        zenohSession.put(keyExpr, payload);
        log.info("Sent command to {}: {}", uavId, cmd.getCommand());
    }
}
```

**配置文件 `zenoh-config.json5`**：

```json5
{
  "mode": "client",
  "connect": {
    "endpoints": ["tcp/zenoh-router:7447"]
  },
  "scouting": {
    "multicast": { "enabled": false }  // 禁用组播，使用TCP
  }
}
```

### 2.4 Zenoh 迁移路径（兼容现有代码）

**阶段1：过渡期（使用 zenoh-bridge-dds）**

```
PX4 ──DDS(局域网)──► zenoh-bridge-dds ──Zenoh──► 现有 dds_gateway.py
                     (无需修改现有代码)
```

- **优点**：现有 `dds_gateway.py` 代码无需修改
- **缺点**：仍依赖局域网DDS

**阶段2：目标架构（纯Zenoh + Java）**

```
PX4 ──Zenoh-Pico(跨公网)──► Zenoh Router ──► Spring Boot ZenohGatewayService
                                             (替代 dds_gateway.py)
```

- **优点**：完全摆脱DDS组播限制，统一Java技术栈
- **改动**：新增 `ZenohGatewayService.java`，移除 `dds_gateway.py`

### 2.5 Zenoh 对整体架构的影响总结

| 层级 | 变化前 | 变化后 | 影响 |
|------|--------|--------|------|
| **无人机通信** | DDS组播(局域网) | Zenoh-Pico(跨公网) | ✅ 支持全球部署 |
| **Gateway** | Python rclpy | **Java zenoh-java** | ✅ 统一技术栈，消除跨语言 |
| **网络要求** | 必须同一局域网 | 只需TCP/UDP可达 | ✅ 支持4G/5G/卫星 |
| **发现机制** | DDS组播发现 | Zenoh Router集中发现 | ✅ 发现更快更可靠 |
| **Kafka集成** | HTTP中转 | **直接Spring Kafka** | ✅ 消除HTTP开销 |
| **Backend** | 不变 | 不变 | ⚪ 无影响 |
| **Frontend** | 不变 | 不变 | ⚪ 无影响 |

**结论**：Zenoh + Java 的组合不仅解决了 DDS 组播限制，还**简化了整体技术栈**，消除了 Python Gateway 层，是架构升级的**最优路径**。

```

│                       无人机层 (Drone Layer)                        │

└────────────────────────────────┬──────────────────────────────────┘
                                 │ Zenoh 路由
                                 ▼

│                    边缘接入层 (Edge Layer)                          │
│  Zenoh Router Cluster (多区域, 支持WAN路由)                         │
│  Gateway Service Cluster (Java Spring Boot, 无状态K8s Pod)         │

└───┬──────────┬──────────┬──────────┬─────────────────────────────┘
    │          │          │          │
    ▼          ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐ ┌──────────┐
│Ingest  │ │Push    │ │Store   │ │Command   │ │DroneState│

│(32实例)│ │(100实例)│ │(16实例)│ │(8实例)   │ │(8实例)   │
└────────┘ └────────┘ └────────┘ └──────────┘ └──────────┘
    │          │          │          │              │
    ▼          ▼          ▼          ▼              ▼
┌───────────────────────────────────────────────────────────────────┐
│                    基础设施层                                       │
│  Redis Cluster (6节点, K8s StatefulSet)                            │
│  Kafka Cluster (10节点, Strimzi Operator)                          │
│  TimescaleDB (主从, 专用服务器, 非容器化)                            │
│  PostgreSQL (业务数据, 专用服务器, 非容器化)                          │

│  Spring Cloud Gateway (API网关, K8s Deployment)                   │
└───────────────────────────────────────────────────────────────────┘
```

### 3.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **Zenoh替代DDS** | 解决组播限制，支持跨公网/跨机房部署，兼容现有ROS2话题 |
| **Java统一技术栈** | 使用zenoh-java消除Python Gateway，简化运维 |
| **按uav_id分区** | 同一无人机的所有数据路由到同一Kafka分区，天然保证有序性 |
| **事件/流分离** | armed变化、连接/断开等走 `events.drone`（低延迟），位置/速度走 `telemetry.raw`（高吞吐） |
| **无状态服务** | 所有业务服务无状态，通过Kafka Consumer Group自动负载均衡 |
| **背压传导** | Kafka分区→Consumer拉模式，天然背压；WebSocket推送设Rate Limiter |
| **消息代际** | 每条消息携带 `epoch`（无人机启动序号），接收端丢弃旧epoch消息 |
| **视口裁剪** | 前端只订阅当前视口范围内的无人机数据，避免千万级数据全量推送 |

## 四、微服务拆分方案

### 4.1 结论：**必须进行微服务拆分**

当前单体 Spring Boot 存在以下**不可调和的矛盾**：

| 矛盾点 | 说明 |
|--------|------|
| **扩展性矛盾** | 遥测接入需要32+实例处理1亿msg/s，但业务API只需要8实例 → 单体扩展浪费资源 |
| **部署耦合** | 修改权限系统需要重启整个Backend，导致所有WebSocket连接断开 |
| **故障传播** | TelemetryPersistenceService 的 OOM 会拖垮整个Backend（包括命令通道） |
| **技术栈异构** | WebSocket推送需要Netty高性能框架，但业务API用Tomcat就够了 |
| **团队扩展** | 单体代码库无法并行开发，千万级系统需要多团队协作 |

### 4.2 推荐拆分方案

```
当前单体                                     目标微服务
────────────────────────────────────────────────────────────────
dds_gateway.py (Python)              ──►  ucs-gateway            (Java, Zenoh订阅→Kafka)
DDSGatewayController.java            ──►  ucs-telemetry-ingest   (Kafka Consumer→Redis)
WebSocketGatewayService.java         ──►  ucs-realtime-push      (Kafka Consumer→WebSocket)
TelemetryPersistenceService.java     ──►  ucs-telemetry-store    (Kafka Consumer→TimescaleDB)
PartitionRoutingService + RedisService ──► ucs-drone-state       (状态管理, Redis Cluster)
ControlService + DdsCommandService   ──►  ucs-command            (命令下发, Kafka)
SecurityConfig + AuthService         ──►  ucs-auth               (认证授权, JWT/OAuth)
Commander/Leader/Pilot Controllers   ──►  ucs-api-gateway        (Spring Cloud Gateway)
RallyPoint/Event/Task Services       ──►  ucs-business           (业务逻辑)
```

### 4.3 微服务详细设计

#### 4.3.1 ucs-gateway（Zenoh网关服务，替代Python Gateway）

**职责**：
- 使用 zenoh-java 订阅 PX4 遥测话题
- 检测事件（armed变化、连接/断开、epoch管理）
- 写入 Kafka（按 uav_id 分区）
- 消费命令 Kafka topic，通过 Zenoh 发送给 PX4

**技术栈**：
- Spring Boot 3.2
- zenoh-java 1.4.0
- Spring Kafka
- CycloneDDS CDRSTREAM（CDR序列化/反序列化）

**扩展策略**：
- 每个 Pod 负责一定范围的无人机（通过环境变量配置）
- K8s HPA 根据 Kafka Consumer Lag 自动扩缩容

#### 4.3.2 ucs-telemetry-ingest（遥测接入服务）

**职责**：
- 从 Kafka `telemetry.raw` topic 消费遥测数据
- 过期消息检测（timestamp 校验）
- 代际检查（epoch 校验，防止断电重连消费旧数据）
- 更新 Redis 最新状态

**关键改进**：

```java
@KafkaListener(topics = "telemetry.raw", groupId = "ingest-group", concurrency = "32")
public void onTelemetry(ConsumerRecord<String, String> record) {
    String uavId = record.key();
    TelemetryMessage msg = deserialize(record.value());
    
    // 1. 过期消息检测（新增）
    long msgAge = System.currentTimeMillis() - msg.getTimestamp();
    if (msgAge > MAX_AGE_MS) {  // 默认5秒
        metrics.counter("telemetry.stale.dropped").increment();
        return;
    }
    
    // 2. 代际检查（新增，防止断电重连消费旧数据）
    long currentEpoch = droneEpochCache.getOrDefault(uavId, 0L);
    if (msg.getEpoch() < currentEpoch) {
        log.warn("Stale epoch for {}: msg={} current={}", uavId, msg.getEpoch(), currentEpoch);
        return;
    }
    
    // 3. 更新Redis最新状态
    redisCluster.hset("drone:" + uavId + ":state", buildStateMap(msg));
    redisCluster.expire("drone:" + uavId + ":state", 30);
}
```

#### 4.3.3 ucs-realtime-push（实时推送服务）

**职责**：
- 从 Kafka 消费遥测数据
- 通过 Redis Pub/Sub 分布式 WebSocket broker 推送
- 按分区路由，只推送关注的无人机数据
- 背压控制（丢帧策略）

**改进**：

```java
@Configuration
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {
    @Override
    public void configureMessageBroker(MessageBrokerRegistry config) {
        // 改用Redis-backed分布式broker（替代SimpleBroker）
        config.enableStompBrokerRelay("/topic", "/queue")
              .setRelayHost(redisHost)
              .setRelayPort(redisPort);
    }
}
```

#### 4.3.4 ucs-telemetry-store（遥测存储服务）

**职责**：
- 从 Kafka 消费遥测数据
- 批量写入 TimescaleDB（COPY 批量写入）

**改进**：

```java
@KafkaListener(topics = "telemetry.raw", groupId = "store-group", concurrency = "16")
public void onTelemetryBatch(List<ConsumerRecord<String, String>> records) {
    // Kafka自带批量消费，无需自己维护无界队列
    List<TelemetryRecord> batch = records.stream()
        .map(r -> deserialize(r.value()))
        .collect(Collectors.toList());
    
    // TimescaleDB COPY批量写入（100万行/s）
    jdbcTemplate.batchUpdate(
        "INSERT INTO uav_telemetry (...) VALUES (...)",
        new BatchPreparedStatementSetter() { /* ... */ }
    );
}
```

#### 4.3.5 ucs-command（命令下发服务）

**职责**：
- 接收前端命令请求
- 写入 Kafka `commands.down` topic（按 uav_id 分区）
- 消费 `commands.ack` topic，更新命令状态

**改进**：

```java
public CompletableFuture<String> sendCommand(String uavId, String commandType, String params) {
    CommandMessage cmd = CommandMessage.builder()
        .commandId(UUID.randomUUID().toString())  // 幂等key
        .uavId(uavId)
        .commandType(commandType)
        .params(params)
        .timestamp(Instant.now())
        .expireAt(Instant.now().plusSeconds(10))   // 10秒过期
        .build();
    
    // 写入Kafka, uav_id做partition key → 命令有序
    return kafkaTemplate.send("commands.down", uavId, toJson(cmd))
        .thenApply(result -> cmd.getCommandId());
}
```

## 五、容器化部署方案

### 5.1 结论：**必须进行容器化部署**

| 原因 | 说明 |
|------|------|
| **水平扩缩容** | 千万级需要数百个 Gateway Pod、数十个服务实例，手动管理不现实 |
| **弹性伸缩** | 无人机数量随任务变化（白天多、夜间少），需要 HPA 自动扩缩 |
| **滚动更新** | 零停机升级，K8s 原生支持 Rolling Update + 就绪探针 |
| **故障自愈** | Pod 崩溃 → K8s 自动重启，节点故障 → Pod 自动迁移 |
| **环境一致性** | 消除"在我机器上能跑"的问题 |
| **资源隔离** | 每个服务的 CPU/内存配额独立，避免互相影响 |

### 5.2 推荐容器编排方案：Kubernetes


## 六、数据库部署策略

### 6.1 结论：**混合部署策略**

| 组件 | 部署方式 | 理由 |
|------|---------|------|
| **TimescaleDB** | **服务器直接部署** | IO密集型，需要本地NVMe极致性能；千万级写入对延迟敏感 |
| **PostgreSQL（业务）** | **服务器直接部署** | 业务数据重要性高，传统备份策略更可控 |
| **Redis Cluster** | **K8s StatefulSet** | 内存型，对磁盘IO不敏感；Redis Operator 成熟 |
| **Kafka Cluster** | **K8s StatefulSet** | Strimzi Operator 非常成熟；Kafka 本身对存储延迟容忍度较高（顺序写） |

### 6.2 方案对比

| 维度 | 容器化部署（K8s StatefulSet） | 服务器直接部署 |
|------|--------------------------|-------------|
| **运维复杂度** | 高（需要 PV/PVC、Operator） | 中（传统 DBA 模式） |
| **性能** | 中（存储有网络开销） | 高（直连本地 NVMe） |
| **弹性扩展** | 好（Operator 自动扩缩） | 差（需手动扩容） |
| **高可用** | 好（K8s + Operator 自动 Failover） | 中（需配置 Patroni/Sentinel） |
| **数据安全** | 中（依赖 PV 快照） | 高（传统备份策略成熟） |
| **成本** | 需要高性能 StorageClass | 需要专用服务器 |

### 6.3 推荐架构

```
┌─────────────────────────────────────────────────────────┐
│                    Kubernetes 集群                        │
│                                                          │
│  所有无状态服务（Gateway、Ingest、Push、Command...）       │
│  Kafka Cluster（Strimzi Operator，StatefulSet）           │
│  Redis Cluster（Redis Operator，StatefulSet）              │
│                                                          │
│  ✅ 优势：弹性扩缩、自动故障恢复、统一运维                  │
└─────────────────────────────────────────────────────────┘
                          │
                          │ 网络连接
                          ▼
┌─────────────────────────────────────────────────────────┐
│                专用数据库服务器（K8s外部）                   │
│                                                          │
│  TimescaleDB (主从复制 + Patroni 自动 Failover)           │
│  PostgreSQL  (业务数据，主从复制)                           │
│                                                          │
│  ✅ 优势：                                                │
│  - 本地 NVMe SSD，IO 性能最优                              │
│  - 成熟的 DBA 运维体系                                     │
│  - 备份/恢复策略可控                                       │
│  - 不受 K8s 调度影响，性能稳定                              │
└─────────────────────────────────────────────────────────┘
```

**简单总结**：
> **关系型数据库放在K8s外面，中间件放在K8s里面。**
> 
> 关系型数据库（TimescaleDB/PG）对IO性能敏感、备份恢复流程复杂、DBA运维体系成熟，适合在专用服务器上部署。
> Kafka 和 Redis 有成熟的 K8s Operator，且对网络存储延迟容忍度相对较高，适合在 K8s 内部署。

### 6.4 TimescaleDB 配置（最小改动，兼容现有 JPA 代码）

```sql
-- 只需一行命令将现有表转为hypertable
SELECT create_hypertable('uav_telemetry', 'timestamp',
    chunk_time_interval => INTERVAL '1 hour',
    number_partitions => 16
);

-- 添加压缩策略 (2小时后自动压缩, 节省80%存储)
ALTER TABLE uav_telemetry SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'uav_id',
    timescaledb.compress_orderby = 'timestamp DESC'
);
SELECT add_compression_policy('uav_telemetry', INTERVAL '2 hours');

-- 数据保留策略 (自动删除7天前数据)
SELECT add_retention_policy('uav_telemetry', INTERVAL '7 days');

-- 连续聚合 (自动生成1分钟聚合, 用于历史轨迹回放)
CREATE MATERIALIZED VIEW telemetry_1min
WITH (timescaledb.continuous) AS
SELECT uav_id,
       time_bucket('1 minute', timestamp) AS bucket,
       avg(lat) AS lat, avg(lon) AS lon, avg(alt) AS alt,
       avg(ground_speed) AS avg_speed
FROM uav_telemetry
GROUP BY uav_id, bucket;
```

## 九、关键问题解答

### Q1：该项目是否需要进行微服务拆分？

**答案：必须拆分。**

**理由**：

1. **扩展性矛盾**：遥测接入需要32+实例处理1亿msg/s，但业务API只需要8实例 → 单体扩展浪费资源
2. **部署耦合**：修改权限系统需要重启整个Backend，导致所有WebSocket连接断开
3. **故障传播**：TelemetryPersistenceService 的 OOM 会拖垮整个Backend（包括命令通道）
4. **技术栈异构**：WebSocket推送需要Netty高性能框架，但业务API用Tomcat就够了
5. **团队扩展**：单体代码库无法并行开发，千万级系统需要多团队协作

**推荐拆分为 8 个微服务**（见第四章）。

### Q2：是否需要容器化部署？

**答案：必须容器化。**

**理由**：

1. **水平扩缩容**：千万级需要数百个 Gateway Pod、数十个服务实例，手动管理不现实
2. **弹性伸缩**：无人机数量随任务变化（白天多、夜间少），需要 HPA 自动扩缩
3. **滚动更新**：零停机升级，K8s 原生支持 Rolling Update + 就绪探针
4. **故障自愈**：Pod 崩溃 → K8s 自动重启，节点故障 → Pod 自动迁移
5. **环境一致性**：消除"在我机器上能跑"的问题
6. **资源隔离**：每个服务的 CPU/内存配额独立，避免互相影响

**推荐使用 Kubernetes**（见第五章）。

### Q3：如果需要容器化部署，数据库是否也需要容器化部署还是直接在服务器部署更好？

**答案：混合部署策略。**

**具体建议**：

| 组件 | 部署方式 | 理由 |
|------|---------|------|
| **TimescaleDB** | **服务器直接部署** | IO密集型，需要本地NVMe极致性能；千万级写入对延迟敏感 |
| **PostgreSQL（业务）** | **服务器直接部署** | 业务数据重要性高，传统备份策略更可控 |
| **Redis Cluster** | **K8s StatefulSet** | 内存型，对磁盘IO不敏感；Redis Operator 成熟（如 Spotahome/redis-operator） |
| **Kafka Cluster** | **K8s StatefulSet** | Strimzi Operator 非常成熟；Kafka 本身对存储延迟容忍度较高（顺序写） |

**简单总结**：
> **关系型数据库放在K8s外面，中间件放在K8s里面。**

**原因**：
- 关系型数据库（TimescaleDB/PG）对IO性能敏感、备份恢复流程复杂、DBA运维体系成熟，适合在专用服务器上部署
- Kafka 和 Redis 有成熟的 K8s Operator，且对网络存储延迟容忍度相对较高，适合在 K8s 内部署

### Q4：Zenoh 会影响 Kafka 以上的架构吗？

**答案：不会。**

Zenoh 只影响 **无人机侧** 和 **Gateway 层**：
- Kafka 以上的所有服务（Backend、Frontend、数据库）完全不受影响
- Gateway 从 `rclpy.subscribe()` 改为 `zenoh.subscribe()`，业务逻辑不变
- 可以使用 `zenoh-bridge-dds` 作为过渡，现有 `dds_gateway.py` 代码无需修改

### Q5：幽灵指令和轨迹偏差问题会被解决吗？

**答案：会。**

通过以下机制：
1. **命令有序性**：Kafka 按 uav_id 分区，同一无人机的命令严格按序执行
2. **命令锁**：Redis 分布式锁防止并发命令竞争
3. **命令过期**：命令携带 `expireAt`，超时未执行自动丢弃
4. **ACK 确认**：命令执行结果通过 `commands.ack` topic 反馈，前端可显示真实执行状态

### Q6：断电重连的过期数据问题会被解决吗？

**答案：会。**

通过 epoch 代际机制：
- 每次无人机连接分配新 epoch（递增整数）
- 所有消息携带 epoch
- 接收端丢弃 epoch 小于当前值的消息
- 断电重连时 State Service 重置所有缓存状态（armed=false 等）

### Q7：为什么选择 Zenoh Java 而不是继续使用 Python Gateway？

**答案：统一技术栈，消除跨语言边界。**

**优势**：
1. **消除跨语言边界**：Java → Java，无序列化开销
2. **统一技术栈**：全Java生态，简化运维
3. **多线程并发**：Java线程池 vs Python GIL
4. **直接Kafka集成**：Spring Kafka 深度集成，无需HTTP中转
5. **更好的可观测性**：Spring Boot Actuator + Micrometer 统一监控

## 附录B：风险提示

1. **Phase 1（引入Kafka）是最低风险、最高收益的改动**，建议立即启动
