# 遥测数据路由分区缓存架构分析

## 一、当前实现分析

### 1.1 现有架构

当前路由分区数据的读写流程（`PartitionRoutingService.java`）：

```
写入流程：
  DB写入（@Transactional） -> Post-Commit Hook -> Redis同步
  失败时 -> ConcurrentLinkedQueue重试（每5秒）
  兜底 -> 定时对账（每60秒DB vs Redis对比修复）

读取流程：
  Redis查询 -> 命中返回
             -> 未命中 -> DB查询 -> 回填Redis -> 返回
             -> DB也无 -> 自动创建默认分区
```

### 1.2 当前实现的优点

1. **Post-Commit Hook保证一致性**：Redis仅在DB事务提交后更新，避免了幻象缓存
2. **重试队列**：Redis写入失败时自动重试，不会丢失更新
3. **定时对账**：60秒间隔的DB-Redis对比修复，作为最后兜底
4. **比延迟双删更可靠**：不依赖时间窗口调优

### 1.3 当前实现的问题

| 问题 | 描述 | 影响 |
|------|------|------|
| **每次遥测都查Redis** | DDS网关每次路由遥测数据时查询Redis获取分区信息 | 大规模无人机 x 10Hz = 数千次/秒Redis查询 |
| **无本地缓存** | 后端/网关没有本地缓存，完全依赖Redis | Redis延迟直接影响遥测延迟 |
| **Redis单点瓶颈** | 所有遥测路由都经过Redis | Redis故障导致所有遥测路由失败 |
| **对账全表扫描** | `reconcileDbRedis` 每60秒全表扫描 | 随无人机数量增长，对账耗时增加 |
| **Post-Commit Hook与业务耦合** | 缓存失效逻辑嵌入业务代码 | 新增写入点时容易遗漏通知 |
| **多实例部署问题** | Post-Commit Hook仅在写入实例执行 | 其他实例的缓存无法被通知失效 |
| **Redis Pub/Sub不可靠** | 实例重启期间丢失Pub/Sub消息 | 重启后的实例持有过期缓存，无法被动失效 |

## 二、推荐方案：Debezium CDC + Kafka + 本地Caffeine缓存

### 2.1 为什么选择Debezium

**关键考量**：

1. **已有Kafka基础设施**：系统已部署Kafka用于遥测数据和命令路由，引入Debezium仅需增加一个Kafka Connect Worker，边际成本极低——不需要新的消息中间件，不需要额外的集群运维
2. **多实例部署的可靠性**：这是选择Debezium而非Redis Pub/Sub的核心原因。Kafka消费者组有offset持久化，实例重启后自动消费所有未处理的变更消息，不会丢失任何通知。而Redis Pub/Sub是fire-and-forget模式，实例下线期间的消息会**永久丢失**——在多实例滚动更新、扩容缩容时这是致命缺陷
3. **WAL监听延迟极低**：PostgreSQL WAL日志变更 -> Debezium捕获 约等于毫秒级；Debezium -> Kafka 约等于毫秒级；Kafka -> 消费者 约等于毫秒级。整条链路端到端延迟通常在 **50-200ms**，完全满足分区路由的实时性需求
4. **与业务代码完全解耦**：Debezium直接监听数据库WAL，不需要在业务代码中手动发通知。无论是哪个服务、哪个SQL修改了分区表，都能自动捕获——后续多实例部署时，任何实例修改DB都会被所有消费者感知
5. **可扩展性**：后续新增需要监听数据库变更的场景（如无人机状态变更、任务分配变更、自动化分区调整），只需新增Debezium Connector配置或添加表到监听列表，无需修改业务代码

### 2.2 关于延迟的澄清

Debezium的延迟经常被高估。以下是各环节的实际延迟：

| 环节 | 延迟 | 说明 |
|------|------|------|
| PG WAL写入 | ~0ms | 事务提交时自动写WAL，零额外开销 |
| Debezium捕获WAL | 1-10ms | PG logical decoding实时流式推送，Debezium通过replication slot接收，无需轮询 |
| Debezium -> Kafka | 1-10ms | Kafka Connect内部管道，内存传输 |
| Kafka -> 消费者 | 1-50ms | 取决于消费者poll间隔（默认100ms，可调至50ms） |
| **端到端总延迟** | **50-200ms** | 远优于60秒定时对账 |

> **为什么延迟不会很大？**
> - Debezium使用PG的逻辑复制协议（streaming replication），WAL变更是**推送**到Debezium的，不是Debezium轮询的
> - Kafka的partition内消息延迟在正常负载下是亚毫秒级
> - 唯一可能导致秒级延迟的场景是Kafka Connect集群CPU饱和或PG WAL slot严重堆积，这在正常运维下不会发生
> - 对比：当前的60秒定时对账意味着分区变更最长需要60秒才能被感知，Debezium将这个延迟降低到毫秒级

### 2.3 整体架构

```
┌──────────────┐
│  PostgreSQL  │
│  WAL日志      │──>  Debezium Connector ──>  Kafka Topic:
│  drone_      │     (Kafka Connect)          "ucsdb.public.drone_partition_map"
│  partition_  │                                     │
│  map 表      │                                     │
└──────────────┘                    ┌────────────────┼────────────────┐
                                    ↓                ↓                ↓
                              后端实例1消费者    后端实例2消费者    DDS网关消费者
                                    │                │                │
                              ┌─────┴─────┐    ┌─────┴─────┐    ┌────┴────┐
                              │更新Redis   │    │更新Redis   │    │失效本地  │
                              │失效本地缓存│    │失效本地缓存│    │缓存      │
                              └───────────┘    └───────────┘    └─────────┘

读取路径（高频）：
遥测数据到达 -> 查Caffeine本地缓存（<1us）
                   │
                   ├── 命中 -> 直接返回
                   │
                   └── 未命中 -> 查Redis -> 回填Caffeine（TTL=5min兜底）
                                  │
                                  └── Redis也未命中 -> 查DB -> 回填Redis + Caffeine
```

### 2.4 为什么只用一个Kafka话题而非两个

原始方案提出了两个话题（话题A用于变更数据，话题B用于缓存失效通知），但这是冗余的：

- **一个话题足够**：Debezium产生的CDC事件本身既包含变更数据，也隐含了缓存失效信号
- **消费者处理流程**：收到CDC事件 -> 先更新Redis -> 再失效本地缓存 -> 下次读取时从Redis回填
- **避免了时序问题**：如果用两个话题，话题B的消费可能早于话题A，导致本地缓存失效后回填时读到Redis中的旧数据。单话题单消费者内顺序处理则不存在此问题

### 2.5 Debezium vs Redis Pub/Sub 对比

| 对比项 | Debezium + Kafka | Redis Pub/Sub |
|--------|-----------------|---------------|
| **消息可靠性** | Kafka持久化 + offset，消息不会丢失 | fire-and-forget，实例离线期间消息永久丢失 |
| **多实例支持** | 消费者组自动负载均衡，新实例自动消费 | 每个实例独立订阅，无负载均衡 |
| **实例重启** | 从上次offset继续消费，不丢失任何变更 | 重启期间所有消息丢失 |
| **与业务解耦** | 完全解耦（监听WAL） | 需要在业务代码中手动PUBLISH |
| **边际成本** | 低（已有Kafka，仅增加Connect Worker） | 低（已有Redis） |
| **延迟** | 50-200ms | 1-10ms |
| **适用场景** | 多实例、高可靠性、大规模部署 | 单实例、容忍丢失 |

**关键结论**：在多实例部署场景下，Redis Pub/Sub的不可靠性是硬伤。Debezium延迟虽略高（50-200ms vs 1-10ms），但对于分区路由变更（人工操作频率）完全可以接受。

## 三、详细配置方案

### 3.1 PostgreSQL WAL配置

PostgreSQL需要启用逻辑复制（logical replication）才能被Debezium监听：

```sql
-- 1. 修改 postgresql.conf（或通过ALTER SYSTEM）
ALTER SYSTEM SET wal_level = 'logical';
ALTER SYSTEM SET max_replication_slots = 4;  -- 至少1个给Debezium
ALTER SYSTEM SET max_wal_senders = 4;        -- 至少1个给Debezium

-- 2. 重启PostgreSQL使配置生效
-- docker-compose restart postgres

-- 3. 验证配置
SHOW wal_level;  -- 应输出 'logical'
SHOW max_replication_slots;  -- 应 >= 4
```

如果使用Docker Compose部署PostgreSQL，在compose文件中添加启动参数：

```yaml
services:
  postgres:
    image: postgres:15
    command: >
      postgres
      -c wal_level=logical
      -c max_replication_slots=4
      -c max_wal_senders=4
    # ... 其他配置不变
```

> **注意**：`wal_level=logical` 会比默认的 `replica` 级别产生略多的WAL日志，但对性能影响极小（<1%）。这也是PG逻辑复制、订阅/发布功能的前提条件，未来其他场景也可能需要。

### 3.2 Docker Compose 中添加 Debezium

在现有的 `docker-compose.yml` 中添加 Kafka Connect（Debezium）服务：

```yaml
services:
  # ... 现有的 postgres, redis, kafka, zookeeper 服务 ...

  debezium-connect:
    image: debezium/connect:2.5
    depends_on:
      - kafka
      - postgres
    ports:
      - "8083:8083"
    environment:
      BOOTSTRAP_SERVERS: kafka:9092
      GROUP_ID: ucs-debezium-connect
      CONFIG_STORAGE_TOPIC: _debezium_configs
      OFFSET_STORAGE_TOPIC: _debezium_offsets
      STATUS_STORAGE_TOPIC: _debezium_statuses
      # 单实例Kafka时 replication factor 必须为1
      CONFIG_STORAGE_REPLICATION_FACTOR: 1
      OFFSET_STORAGE_REPLICATION_FACTOR: 1
      STATUS_STORAGE_REPLICATION_FACTOR: 1
      # 性能调优：减少消息发送延迟
      CONNECT_PRODUCER_LINGER_MS: 5
      CONNECT_CONSUMER_MAX_POLL_INTERVAL_MS: 300000
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8083/"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped
    # 资源限制（生产环境建议设置）
    deploy:
      resources:
        limits:
          memory: 1G
        reservations:
          memory: 512M
```

> **资源开销**：Debezium Connect Worker 默认占用约256-512MB内存。只监听一张表时CPU开销极低（<1%）。

### 3.3 注册 Debezium Connector

Debezium Connect 启动后（约10-15秒），通过REST API注册PostgreSQL Connector。

建议创建初始化脚本 `scripts/init-debezium.sh`：

```bash
#!/bin/bash
# 等待 Debezium Connect 就绪
echo "Waiting for Debezium Connect..."
until curl -sf http://localhost:8083/; do
  sleep 2
done
echo "Debezium Connect is ready."

# 注册 PostgreSQL Connector
curl -X POST http://localhost:8083/connectors \
  -H "Content-Type: application/json" \
  -d '{
    "name": "ucs-partition-connector",
    "config": {
        "connector.class": "io.debezium.connector.postgresql.PostgresConnector",

        "database.hostname": "postgres",
        "database.port": "5432",
        "database.user": "ucs_user",
        "database.password": "'"${POSTGRES_PASSWORD}"'",
        "database.dbname": "ucs_db",

        "topic.prefix": "ucsdb",
        "plugin.name": "pgoutput",
        "slot.name": "ucs_partition_slot",
        "publication.name": "ucs_partition_pub",

        "table.include.list": "public.drone_partition_map",

        "key.converter": "org.apache.kafka.connect.json.JsonConverter",
        "key.converter.schemas.enable": false,
        "value.converter": "org.apache.kafka.connect.json.JsonConverter",
        "value.converter.schemas.enable": false,

        "transforms": "unwrap",
        "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
        "transforms.unwrap.drop.tombstones": true,
        "transforms.unwrap.add.fields": "op,table,ts_ms",

        "heartbeat.interval.ms": 60000,
        "snapshot.mode": "initial",

        "errors.log.enable": true,
        "errors.log.include.messages": true,
        "errors.tolerance": "all",
        "errors.deadletterqueue.topic.name": "ucs_dlq",
        "errors.deadletterqueue.context.headers.enable": true
    }
}'

echo ""
echo "Connector registered. Verifying..."
curl -s http://localhost:8083/connectors/ucs-partition-connector/status | python3 -m json.tool
```

**核心参数说明**：

| 参数 | 值 | 说明 |
|------|-----|------|
| `topic.prefix` | `ucsdb` | Kafka topic名 = `{prefix}.{schema}.{table}` |
| `table.include.list` | `public.drone_partition_map` | **只监听分区映射表**，最小化WAL流量和Kafka写入 |
| `plugin.name` | `pgoutput` | PG 10+ 内置逻辑解码插件，**无需安装额外PG扩展** |
| `snapshot.mode` | `initial` | 首次启动全量快照（确保Kafka有完整当前状态），之后仅增量CDC |
| `transforms.unwrap` | `ExtractNewRecordState` | 简化消息格式：只提取变更后的行数据，去掉Debezium envelope |
| `heartbeat.interval.ms` | `60000` | 每60秒心跳，**防止WAL slot堆积**（即使长时间无表变更） |
| `errors.tolerance` | `all` | 单条消息处理失败不阻塞Connector，送入DLQ |

### 3.4 Kafka Topic 配置

Debezium会自动创建Topic `ucsdb.public.drone_partition_map`。建议预先创建并设置压缩策略：

```bash
kafka-topics.sh --create \
  --bootstrap-server kafka:9092 \
  --topic ucsdb.public.drone_partition_map \
  --partitions 3 \
  --replication-factor 1 \
  --config retention.ms=604800000 \
  --config cleanup.policy=compact,delete
```

- **`cleanup.policy=compact`**：Log Compaction保留每个key的最新值。新启动的消费者不需要从topic起始位置消费全部历史，只需读取每个key的最新状态即可获得完整的当前分区映射
- **`retention.ms=7天`**：与compaction配合，保证消息在7天内可回溯

### 3.5 CDC消息格式

经过 `ExtractNewRecordState` 转换后的消息格式（简洁直观）：

```json
{
  "id": 42,
  "drone_id": 5,
  "uav_id": "px4_3",
  "partition_name": "leader_01",
  "is_active": true,
  "created_at": "2024-01-15T10:30:00Z",
  "updated_at": "2024-01-15T10:30:00Z",
  "__op": "u",
  "__table": "drone_partition_map",
  "__ts_ms": 1712345678901
}
```

- `__op`：操作类型 -- `c`=INSERT, `u`=UPDATE, `d`=DELETE, `r`=快照读
- 删除消息中 `is_active` 可能为null，需要消费者处理

## 四、后端消费者实现

### 4.1 监听方式说明

**是Redis监听还是后端服务的消费者监听？**

答：**后端服务的Kafka消费者监听**。

具体来说：
- 每个后端服务实例内启动一个 `@KafkaListener`，监听CDC话题 `ucsdb.public.drone_partition_map`
- 每个DDS网关实例内启动一个Kafka消费者线程，监听同一话题
- 使用**不同的消费者组**：后端用 `ucs-partition-cache-updater`，DDS网关用 `dds-gateway-partition-cache`
- 不同消费者组意味着**每个组都能收到全部消息**（广播语义）
- 同一组内的多个实例，Kafka自动做partition级负载均衡

为什么不用Redis监听：
- Redis Pub/Sub是fire-and-forget，无法保证消息可靠送达
- Redis Keyspace Notifications同样不持久化
- 后端实例重启期间的变更消息会永久丢失

### 4.2 Java后端：Kafka CDC消费者

```java
@Component
@Slf4j
public class PartitionCdcConsumer {

    private final PartitionCacheService cacheService;
    private final RedisService redisService;
    private final DronePartitionMapRepository repository;
    private final ObjectMapper objectMapper;

    /**
     * 监听Debezium CDC事件，处理分区路由变更。
     *
     * 处理流程：
     * 1. 解析CDC消息，提取uavId
     * 2. 从DB加载该uavId的最新分区数据（DB是唯一真相源）
     * 3. 更新Redis
     * 4. 失效本地Caffeine缓存（下次读取时从Redis回填）
     *
     * 为什么从DB重新加载而不是直接用CDC消息中的数据？
     * - CDC消息只包含单行变更，但一个uavId可能有多行分区映射
     * - 批量UPDATE时CDC消息可能乱序到达
     * - DB查询保证获取到最终一致的完整状态
     */
    @KafkaListener(
        topics = "ucsdb.public.drone_partition_map",
        groupId = "ucs-partition-cache-updater",
        concurrency = "1"
    )
    public void onPartitionChange(String message) {
        try {
            JsonNode node = objectMapper.readTree(message);
            String uavId = node.path("uav_id").asText(null);
            String op = node.path("__op").asText("");

            if (uavId == null || uavId.isEmpty()) {
                log.warn("[CDC] Received message without uav_id: {}", message);
                return;
            }

            log.info("[CDC] Partition change detected: uavId={}, op={}", uavId, op);

            // Step 1: 从DB加载最新完整状态
            List<String> dbPartitions = repository
                .findActivePartitionNamesByUavId(uavId);
            Set<String> partitionSet = new LinkedHashSet<>(dbPartitions);

            // Step 2: 更新Redis（尽力而为，失败不阻塞）
            try {
                redisService.setDronePartitions(uavId, partitionSet);
                for (String partition : partitionSet) {
                    redisService.addDroneToPartition(uavId, partition);
                }
            } catch (Exception e) {
                log.error("[CDC] Redis update failed for {}: {}", uavId, e.getMessage());
                // 不抛异常，让Kafka提交offset
                // Redis数据会在下次CDC事件或定时对账时修复
            }

            // Step 3: 失效本地缓存
            cacheService.invalidate(uavId);

            log.info("[CDC] Cache updated: uavId={}, partitions={}", uavId, partitionSet);

        } catch (Exception e) {
            log.error("[CDC] Failed to process partition change: {}", e.getMessage(), e);
        }
    }
}
```

### 4.3 Java后端：本地Caffeine缓存服务

```java
@Service
@Slf4j
public class PartitionCacheService {

    /**
     * 本地缓存：uavId -> Set<partitionName>
     *
     * TTL=5分钟作为兜底：
     * - 正常情况下，CDC消费者会主动失效缓存，TTL不会生效
     * - 异常情况下（CDC延迟、Kafka故障），TTL保证缓存最终过期
     *
     * maximumSize=10000：支持大规模无人机集群
     */
    private final Cache<String, Set<String>> localCache = Caffeine.newBuilder()
            .maximumSize(10000)
            .expireAfterWrite(5, TimeUnit.MINUTES)
            .recordStats()
            .build();

    private final RedisService redisService;
    private final DronePartitionMapRepository repository;

    /**
     * 高频读取入口 - 遥测路由时调用。
     *
     * 三级回源策略：
     *   本地缓存（<1us） -> Redis（~1ms） -> DB（~5ms）
     *
     * 任何一级不可用都会自动降级到下一级。
     */
    public Set<String> getPartitions(String uavId) {
        return localCache.get(uavId, this::loadFromRedisOrDb);
    }

    private Set<String> loadFromRedisOrDb(String uavId) {
        // 先查Redis
        try {
            Set<String> redis = redisService.getDronePartitions(uavId);
            if (!redis.isEmpty()) {
                return redis;
            }
        } catch (Exception e) {
            log.warn("[PartitionCache] Redis unavailable for {}, falling back to DB: {}",
                     uavId, e.getMessage());
        }

        // Redis未命中或不可用，查DB（最终兜底）
        List<String> db = repository.findActivePartitionNamesByUavId(uavId);
        if (!db.isEmpty()) {
            Set<String> result = new LinkedHashSet<>(db);
            // 尝试回填Redis（尽力而为）
            try {
                redisService.setDronePartitions(uavId, result);
            } catch (Exception e) {
                log.warn("[PartitionCache] Redis write-back failed for {}: {}",
                         uavId, e.getMessage());
            }
            return result;
        }

        return Collections.emptySet();
    }

    /** CDC消费者调用：失效指定uavId的本地缓存 */
    public void invalidate(String uavId) {
        localCache.invalidate(uavId);
    }

    /** 全量失效（Redis故障恢复、服务启动时调用） */
    public void invalidateAll() {
        localCache.invalidateAll();
    }

    /** 缓存统计（用于监控Dashboard） */
    public CacheStats getStats() {
        return localCache.stats();
    }
}
```

### 4.4 DDS网关（Python端）本地缓存 + Kafka CDC消费者

```python
import threading
import time
import json
from kafka import KafkaConsumer

class PartitionLocalCache:
    """
    DDS网关本地分区缓存。

    读取路径：本地dict -> Redis -> 返回None（由调用方处理）
    失效方式：Kafka CDC消费者线程收到变更通知后失效
    兜底：TTL=300秒自动过期
    """

    def __init__(self, redis_client, ttl_seconds=300):
        self._cache = {}        # uavId -> (partitions, expire_time)
        self._redis = redis_client
        self._ttl = ttl_seconds
        self._lock = threading.Lock()

    def get_partitions(self, uav_id):
        now = time.time()
        with self._lock:
            entry = self._cache.get(uav_id)
            if entry and entry[1] > now:
                return entry[0]

        # 本地缓存未命中/过期，查Redis
        try:
            partitions = self._redis.smembers(f"drone:partitions:{uav_id}")
            if partitions:
                with self._lock:
                    self._cache[uav_id] = (partitions, now + self._ttl)
                return partitions
        except Exception:
            pass

        return None

    def invalidate(self, uav_id):
        with self._lock:
            self._cache.pop(uav_id, None)

    def invalidate_all(self):
        with self._lock:
            self._cache.clear()


class PartitionCdcListener:
    """
    监听Debezium CDC Kafka话题，收到分区变更时失效本地缓存。

    使用独立消费者组 'dds-gateway-partition-cache'，
    确保每个DDS网关实例都能收到全部变更消息。
    """

    def __init__(self, kafka_brokers, cache,
                 topic='ucsdb.public.drone_partition_map',
                 group_id='dds-gateway-partition-cache'):
        self._cache = cache
        self._topic = topic
        self._consumer = KafkaConsumer(
            topic,
            bootstrap_servers=kafka_brokers,
            group_id=group_id,
            auto_offset_reset='latest',
            value_deserializer=lambda m: json.loads(m.decode('utf-8')),
            max_poll_interval_ms=300000,
            session_timeout_ms=30000,
        )
        self._running = True

    def start(self):
        t = threading.Thread(target=self._consume_loop, daemon=True,
                             name='partition-cdc-listener')
        t.start()
        return t

    def _consume_loop(self):
        while self._running:
            try:
                records = self._consumer.poll(timeout_ms=500)
                for tp, messages in records.items():
                    for msg in messages:
                        uav_id = msg.value.get('uav_id')
                        if uav_id:
                            self._cache.invalidate(uav_id)
            except Exception as e:
                time.sleep(1)  # 短暂退避后重试

    def stop(self):
        self._running = False
        try:
            self._consumer.close()
        except Exception:
            pass
```

## 五、Redis故障处理策略

### 5.1 三级降级机制

```
正常模式：  本地缓存(Caffeine) <-- CDC失效 <-- Redis <-- CDC更新 <-- DB
降级模式1： Redis短暂不可用（<5min） -> 本地缓存TTL内继续正常服务
降级模式2： Redis长期不可用（>5min） -> TTL过期后直接查DB回填本地缓存
降级模式3： DB不可用 -> 本地缓存+Redis缓存兜底（最终缓存全部过期后服务降级）
```

### 5.2 各故障场景及处理

| 故障场景 | 影响 | 自动处理 | 人工恢复 |
|---------|------|---------|---------|
| **Redis短暂不可用**（<5min） | 本地缓存TTL内正常 | TTL自动兜底 | 无需干预 |
| **Redis长时间不可用**（>5min） | TTL过期后读取变慢（查DB） | 自动降级查DB | Redis恢复后自动回填 |
| **Redis数据丢失**（重启无持久化） | 首次查询回源DB | CDC消费者重建 + DB回填 | 无需干预 |
| **Kafka暂时不可用** | CDC消息积压 | 本地缓存TTL兜底 | Kafka恢复后自动消费积压 |
| **Debezium Connector故障** | 停止捕获新变更 | TTL兜底 + 定时对账 | 重启Connector |
| **后端实例重启** | 本地缓存清空 | 从Kafka offset恢复 + Redis回填 | 无需干预 |
| **DDS网关实例重启** | 本地缓存清空 | Redis回填 + CDC消费者恢复 | 无需干预 |

### 5.3 Redis更新失败时的处理策略

```java
// CDC消费者中的Redis更新失败处理
@KafkaListener(topics = "ucsdb.public.drone_partition_map", ...)
public void onPartitionChange(String message) {
    // ... 解析uavId, 从DB加载最新状态 ...

    // 更新Redis（可能失败）
    boolean redisUpdated = false;
    try {
        redisService.setDronePartitions(uavId, partitionSet);
        redisUpdated = true;
    } catch (Exception e) {
        log.error("[CDC] Redis update failed for {}: {}", uavId, e.getMessage());
        // 不抛异常 - 让Kafka提交offset，避免无限重试
        // Redis数据会在以下时机自动修复：
        // 1. 下一次同一uavId的CDC事件
        // 2. 定时对账（每5分钟）
        // 3. 本地缓存TTL过期后的DB回填
    }

    // 无论Redis是否成功，都失效本地缓存
    // 这样下次读取时：
    //   Redis可用 -> 从Redis回填（可能是旧数据，但定时对账会修复）
    //   Redis不可用 -> 直接查DB回填（保证正确性）
    cacheService.invalidate(uavId);
}
```

## 八、总结

| 项目 | 方案 | 说明 |
|------|------|------|
| **CDC机制** | Debezium + Kafka | 已有Kafka，边际成本低；多实例可靠；与业务完全解耦 |
| **Kafka话题** | 单话题 | `ucsdb.public.drone_partition_map`，避免双话题时序问题 |
| **本地缓存** | Caffeine（Java）/ dict+TTL（Python） | 消除高频遥测路由对Redis的依赖，延迟<1us |
| **缓存失效** | CDC消费者主动失效 + TTL=5min兜底 | CDC保证实时性，TTL保证最终一致性 |
| **Redis角色** | L2缓存（本地缓存与DB之间） | 降级为二级缓存，不再是关键路径上的单点 |
| **DB角色** | 唯一真相源（Source of Truth） | 所有修复和回填都以DB为准 |
| **监听方式** | **后端服务的Kafka消费者**监听CDC话题 | 不是Redis自身监听；每个实例独立消费全部消息 |
| **定时对账** | 保留但降频至300秒 | 检测CDC链路异常的兜底手段，非主要同步机制 |
| **Redis故障** | 三级降级：本地缓存 -> DB直查 -> 空集合告警 | 任何单点故障不导致系统完全不可用 |
| **延迟** | 端到端50-200ms（WAL->Debezium->Kafka->消费者） | 远优于60秒对账，对分区变更频率完全足够 |
