# 遥测数据路由分区缓存架构分析

## 一、当前实现分析

### 1.1 现有架构

当前路由分区数据的读写流程（`PartitionRoutingService.java`）：

```
写入流程：
  DB写入（@Transactional） → Post-Commit Hook → Redis同步
  失败时 → ConcurrentLinkedQueue重试（每5秒）
  兜底 → 定时对账（每60秒DB vs Redis对比修复）

读取流程：
  Redis查询 → 命中返回
             → 未命中 → DB查询 → 回填Redis → 返回
             → DB也无 → 自动创建默认分区
```

### 1.2 当前实现的优点

1. **Post-Commit Hook保证一致性**：Redis仅在DB事务提交后更新，避免了幻象缓存
2. **重试队列**：Redis写入失败时自动重试，不会丢失更新
3. **定时对账**：60秒间隔的DB-Redis对比修复，作为最后兜底
4. **比延迟双删更可靠**：不依赖时间窗口调优

### 1.3 当前实现的问题

| 问题 | 描述 | 影响 |
|------|------|------|
| **每次遥测都查Redis** | DDS网关每次路由遥测数据时查询Redis获取分区信息 | 30架无人机 × 10Hz = 300次/秒Redis查询 |
| **无本地缓存** | 后端/网关没有本地缓存，完全依赖Redis | Redis延迟直接影响遥测延迟 |
| **Redis单点瓶颈** | 所有遥测路由都经过Redis | Redis故障导致所有遥测路由失败 |
| **对账开销** | `reconcileDbRedis` 每60秒全表扫描 | 随无人机数量增长，对账耗时增加 |
| **无变更通知** | 分区变更依赖定时对账发现 | 最长60秒延迟感知变更 |

## 二、用户提出的方案分析

### 2.1 提出的方案：Debezium + Kafka + 本地缓存

```
PG数据库 → Debezium(WAL监听) → Kafka话题A(变更数据)
                                    ↓
                              后端消费者 → 更新Redis
                                    ↓
                              Kafka话题B(缓存失效通知)
                                    ↓
                              后端消费者 → 失效本地缓存 → 被动从Redis回填
```

### 2.2 方案评估

#### 优点
- **实时变更感知**：Debezium监听WAL，变更延迟<1秒（远优于60秒对账）
- **本地缓存降低Redis压力**：遥测路由直接查本地缓存，Redis压力降为0
- **事件驱动**：Kafka话题驱动缓存更新，比轮询更高效

#### 存在的问题

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **架构复杂度过高** | 高 | 引入Debezium + 2个Kafka话题 + 消费者，仅为解决分区路由缓存 |
| **Debezium运维成本** | 高 | 需要配置PG WAL级别、Debezium Connect集群、Schema Registry |
| **两个Kafka话题冗余** | 中 | 话题A（变更数据）和话题B（失效通知）本质上是同一个事件 |
| **Redis更新与本地缓存失效的时序** | 中 | 若消费者先失效本地缓存再更新Redis，回填时可能读到旧Redis数据 |
| **Debezium延迟不一定更低** | 中 | WAL→Debezium→Kafka→消费者的链路延迟可能>直接Post-Commit Hook |
| **分区数据变更频率极低** | 关键 | 分区路由只在操作员手动修改时变更，频率<<1次/分钟 |

#### 核心矛盾

**分区路由数据的特点是：读频率极高（300次/秒），写频率极低（手动操作，<1次/小时）。** 这是一个典型的"读多写少"场景，最优解是**本地缓存 + 简单失效机制**，而非引入重量级CDC管道。

## 三、推荐方案：本地Caffeine缓存 + Redis Pub/Sub失效

### 3.1 架构

```
                写入路径（极低频）
                ────────────────
DB写入(@Transactional)
    │
    ├── Post-Commit Hook → Redis SET（已有）
    │
    └── Post-Commit Hook → Redis PUBLISH "partition:invalidate" {uavId}
                                │
              ┌─────────────────┼─────────────────┐
              ↓                 ↓                 ↓
         DDS网关实例1      DDS网关实例2      后端服务实例
         Caffeine失效      Caffeine失效      Caffeine失效

                读取路径（极高频）
                ────────────────
遥测数据到达 → 查Caffeine本地缓存
                   │
                   ├── 命中 → 直接返回（<1us）
                   │
                   └── 未命中 → 查Redis → 回填Caffeine（TTL=5min）
                                  │
                                  └── Redis也未命中 → 查DB → 回填Redis+Caffeine
```

### 3.2 为什么选择这个方案

| 对比项 | Debezium方案 | 本地缓存+Pub/Sub方案 |
|--------|------------|-------------------|
| 新增组件 | Debezium Connect + 2个Kafka话题 | Caffeine依赖（JAR包） |
| 运维复杂度 | 高（WAL配置、Debezium集群） | 低（零额外运维） |
| 变更感知延迟 | ~1-3秒（WAL→Debezium→Kafka→消费者） | ~1-10ms（Redis Pub/Sub） |
| 读取延迟 | 本地缓存<1us（相同） | 本地缓存<1us（相同） |
| Redis压力 | 仍需要Redis作为中间层 | 仅缓存未命中时查Redis |
| 故障影响 | Debezium故障→缓存无法更新 | Redis故障→TTL兜底（5分钟旧数据） |
| 适合场景 | 高频数据变更、多系统同步 | 低频变更、高频读取 |

### 3.3 实现方案

#### 3.3.1 Java后端：本地Caffeine缓存

```java
@Service
public class PartitionCacheService {

    // 本地缓存：uavId -> Set<partitionName>
    // TTL=5分钟（兜底），最大1000条
    private final Cache<String, Set<String>> localCache = Caffeine.newBuilder()
            .maximumSize(1000)
            .expireAfterWrite(5, TimeUnit.MINUTES)
            .build();

    private final RedisService redisService;
    private final DronePartitionMapRepository repository;

    /**
     * 高频读取入口 - 遥测路由时调用
     * 优先级：本地缓存 → Redis → DB
     */
    public Set<String> getPartitions(String uavId) {
        return localCache.get(uavId, key -> {
            // 本地缓存未命中，查Redis
            Set<String> redis = redisService.getDronePartitions(key);
            if (!redis.isEmpty()) return redis;
            // Redis也未命中，查DB
            List<String> db = repository.findActivePartitionNamesByUavId(key);
            if (!db.isEmpty()) {
                Set<String> result = new LinkedHashSet<>(db);
                redisService.setDronePartitions(key, result);
                return result;
            }
            return Collections.emptySet();
        });
    }

    /**
     * 缓存失效 - 收到Pub/Sub消息时调用
     */
    public void invalidate(String uavId) {
        localCache.invalidate(uavId);
        log.info("[PartitionCache] Invalidated local cache for '{}'", uavId);
    }

    /**
     * 全量失效 - Redis故障恢复时调用
     */
    public void invalidateAll() {
        localCache.invalidateAll();
        log.info("[PartitionCache] Invalidated all local cache");
    }
}
```

#### 3.3.2 Redis Pub/Sub 监听

public class PartitionInvalidateListener {

    private final PartitionCacheService cacheService;

#### 3.3.4 DDS网关（Python端）本地缓存

```python
# dds_gateway.py 中的本地缓存
class PartitionLocalCache:
    """Local cache for partition routing with TTL fallback."""

    def __init__(self, redis_client, ttl_seconds=300):
        self._cache = {}        # uavId -> (partitions, expire_time)
        self._redis = redis_client
        self._ttl = ttl_seconds
        self._lock = threading.Lock()

    def get_partitions(self, uav_id):
        now = time.time()
        with self._lock:
            entry = self._cache.get(uav_id)
            if entry and entry[1] > now:
                return entry[0]

        # Cache miss, query Redis
        try:
            partitions = self._redis.smembers(f"drone:partitions:{uav_id}")
            if partitions:
                with self._lock:
                    self._cache[uav_id] = (partitions, now + self._ttl)
                return partitions
        except Exception:
            pass

        return None

    def invalidate(self, uav_id):
        with self._lock:
            self._cache.pop(uav_id, None)
```

### 3.4 Redis故障处理

| 故障场景 | 影响 | 处理策略 |
|---------|------|---------|
| Redis短暂不可用（<5分钟） | 本地缓存TTL内正常服务 | TTL兜底，无需干预 |
| Redis长时间不可用（>5分钟） | TTL过期后本地缓存失效 | 直接查DB回填本地缓存（跳过Redis） |
| Redis恢复后数据丢失 | Redis为空 | 触发warmUpCache()从DB重建 |
| Pub/Sub消息丢失 | 某实例本地缓存未失效 | TTL兜底（最多5分钟旧数据） |
| Redis写入失败 | 本地缓存不受影响 | 重试队列（已有机制）|

关键设计：**本地缓存读取路径中，DB是最终兜底，不依赖Redis可用性。**

```java
public Set<String> getPartitionsWithFallback(String uavId) {
    // 1. 本地缓存
    Set<String> local = localCache.getIfPresent(uavId);
    if (local != null) return local;

    // 2. Redis（可能不可用）
    try {
        Set<String> redis = redisService.getDronePartitions(uavId);
        if (!redis.isEmpty()) {
            localCache.put(uavId, redis);
            return redis;
        }
    } catch (Exception e) {
        log.warn("[Cache] Redis unavailable, falling back to DB");
    }

    // 3. DB（最终兜底）
    List<String> db = repository.findActivePartitionNamesByUavId(uavId);
    Set<String> result = db.isEmpty()
        ? Collections.emptySet()
        : new LinkedHashSet<>(db);
    localCache.put(uavId, result);
    return result;
}
```

## 四、关于是否引入Debezium的建议

### 4.1 当前不建议引入Debezium

**原因**：
1. 分区路由数据变更频率极低（操作员手动操作），不需要CDC级别的实时性
2. 当前Post-Commit Hook已能在<100ms内完成Redis同步
3. Debezium引入了显著的运维复杂度（WAL配置、Connector管理、Schema演进）
4. 系统当前阶段应优先解决DDS网关性能瓶颈，而非过度设计缓存层

### 4.2 何时应考虑引入Debezium

当系统满足以下条件时，可以考虑：
- 无人机数量 > 500架，多个微服务需要同步分区数据
- 需要跨系统数据同步（如数据湖、分析平台）
- 分区数据变更频率显著增加（如自动化分区调整）
- 已有Kafka Connect集群基础设施

### 4.3 Debezium引入时的注意事项

如果后续确实需要引入Debezium，建议：

1. **单话题而非双话题**：只需一个Kafka话题传输变更数据，消费者同时更新Redis和失效本地缓存
2. **幂等消费者**：确保消费者处理是幂等的（重复消费不会造成数据不一致）
3. **使用Debezium Outbox模式**：而非直接监听表WAL，减少与表结构的耦合
4. **保留TTL兜底**：本地缓存始终设置TTL，作为所有失效机制的最后防线

## 五、总结

| 项目 | 推荐 |
|------|------|
| 本地缓存 | Caffeine（Java）/ dict+TTL（Python），必须实现 |
| 缓存失效 | Redis Pub/Sub，简单可靠 |
| TTL兜底 | 5分钟，防止任何失效机制失败 |
| Redis故障处理 | DB直接回填本地缓存（跳过Redis） |
| Debezium | 当前阶段不引入，500+架无人机规模时再考虑 |
| 监听方式 | 后端消费者监听Redis Pub/Sub频道（非Redis自身监听） |
