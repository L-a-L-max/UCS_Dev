## 2. 性能瓶颈全链路分析

### 2.1 瓶颈优先级矩阵

按影响严重程度和紧迫性排序：

| 优先级 | 瓶颈位置 | 瓶颈描述 | 影响规模 | 修复复杂度 |
|-------|---------|---------|---------|-----------|
| **P0-致命** | TelemetryKafkaConsumer | 消费处理同步阻塞：每条消息执行 Redis写+DB写+WebSocket广播 | 10架即阻塞 | 中 |
| **P0-致命** | WebSocket SimpleBroker | 内存级STOMP Broker无法集群共享，全量广播所有无人机数据 | 无法多实例 | 高 |
| **P0-致命** | TelemetryPersistenceService | 5s flush周期，单线程batch上限1000条，1000架=50000条/5s溢出 | 500架+ | 中 |
| **P1-严重** | DDS/MAVLink Gateway 单实例 | 单进程处理所有无人机数据收发和Kafka生产 | 200架+ | 中 |
| **P1-严重** | Kafka 单Broker | 无高可用、无数据冗余、ISR机制不生效 | 生产环境 | 中 |
| **P1-严重** | PostgreSQL/TimescaleDB 单实例 | 写入竞争、无连接池调优、无读写分离 | 500架+ | 高 |
| **P2-重要** | Redis 单节点 | 高频setDroneOnline(每条遥测)打穿Redis | 1000架+ | 低 |
| **P2-重要** | 前端全量渲染 | 1000个Marker + STOMP全量推送导致浏览器卡顿 | 500架+ | 中 |
| **P2-重要** | PartitionRoutingService | 每条消息查Redis→可能穿透DB→事务创建记录 | 新无人机接入 | 低 |
| **P3-改善** | EpochManager 内存态 | 后端重启丢失所有epoch，导致短暂僵尸数据接受 | 重启时 | 低 |
| **P3-改善** | 日志输出过多 | 每条消息多处log.info()影响IO性能 | 高吞吐时 | 低 |
| **P3-改善** | Kafka序列化 | JSON文本序列化，不如Protobuf/Avro高效 | 高吞吐时 | 中 |

### 2.2 消费端处理链路详细分析

当前 `TelemetryKafkaConsumer.consumeTelemetry()` 的处理流程（**全部串行**）：

```
消息到达 (String JSON)
  │
  ├─ ① JSON反序列化: objectMapper.readValue()              ~0.05ms
  ├─ ② Epoch校验: epochManager.validateEpoch()              ~0.01ms (ConcurrentHashMap)
  ├─ ③ 时间戳校验: Instant.parse()                          ~0.02ms
  ├─ ④ Redis在线标记: redisService.setDroneOnline()         ~0.5-2ms (网络RTT)
  ├─ ⑤ DB持久化: telemetryPersistenceService.persistFromMap() ~0.01ms (仅入buffer)
  ├─ ⑥ 分区路由: partitionRoutingService.getPartitionsForDrone()
  │     ├─ Redis查询: ~0.5-2ms (命中)
  │     └─ DB查询+事务: ~5-50ms (未命中, 含autoCreateDrone)
  ├─ ⑦ WebSocket广播(分区): broadcastToPartitions()          ~0.5-5ms
  └─ ⑧ WebSocket广播(全量): broadcastAll()                   ~0.5-5ms
  
  最佳情况单条处理: ~2-4ms → 理论上限 250-500 msg/s (单线程)
  concurrency=4 → 理论上限 1000-2000 msg/s
  
  实际情况：
  - Redis网络波动 → 某条消息耗时10ms+
  - 分区路由Cache MISS → 50ms+ 
  - WebSocket广播大量客户端 → 5ms+
  - GC暂停 → 偶发10-50ms
  → 实际上限 ~500-800 msg/s，100 msg/s(10架)已开始出现lag
```

**核心问题：消费处理和广播是串行绑定的。** 应该解耦为：消费→写缓冲、独立线程→广播、独立线程→持久化。

### 2.3 WebSocket 广播瓶颈

当前 `WebSocketConfig` 使用 `SimpleBroker`：

```java
config.enableSimpleBroker("/topic", "/queue");
```

**问题：**
1. `SimpleBroker` 是Spring内置的内存级消息分发器，所有订阅关系保存在JVM堆中
2. **无法跨实例共享**：后端启动多实例时，客户端A连接实例1、客户端B连接实例2，实例1发送的消息只能到达客户端A
3. 当前 `broadcastAll()` 发送 **所有无人机** 的遥测数据到 `/topic/telemetry`，即每个前端客户端每100ms接收全部1000架无人机数据
4. `broadcastDroneStatus()` 每2秒调用 `droneService.getAllDrones()` 查询数据库全表

**数据量计算（1000架）：**
- 每条遥测推送 ~500B × 1000架 = 500KB/次
- 10Hz推送 = 5MB/s/客户端
- 10个客户端 = 50MB/s WebSocket出带宽（仅遥测数据）
- STOMP协议overhead约20%，实际 ~60MB/s

### 2.4 网关层瓶颈

**DDS Gateway (`dds_gateway.py`)：**

```python
# 主循环结构
while self.running and rclpy.ok():
    # 1. 每5s发现新Topic（同步阻塞）
    new_drones = self.discover_drones_from_topics()  # rclpy API调用
    
    # 2. 遍历所有无人机，构建batch
    for uid in uav_ids_snapshot:
        with lock:  # 细粒度锁，但仍然串行遍历
            ...
    
    # 3. 发送Kafka（同步但async send）
    self.send_to_kafka(batch_payload)
    
    time.sleep(0.05)  # 20Hz主循环
```

**瓶颈分析：**
- ROS2 spin线程 + 主循环线程：spin处理DDS回调，主循环聚合发送。当无人机数量增加，spin线程处理回调的速率成为瓶颈
- `_drone_locks` 使用 `defaultdict(threading.Lock)`，1000架无人机=1000把锁，但主循环串行遍历所有锁
- Kafka Producer同步调用（虽然内部是async，但构建消息和序列化仍是串行的）
- 单进程GIL限制：Python的GIL使得多线程无法真正并行CPU操作

**MAVLink Gateway (`mavlink_gateway.py`)：**
- 单UDP socket接收所有无人机数据：`_udp_loop` 在一个线程中 `recvfrom` → `_parse_mavlink_bytes` → `_dispatch_mavlink_message`
- 解析和分发是串行的，每条MAVLink消息解析约0.1-0.5ms
- 理论上限：2000-10000 msg/s（取决于消息大小和CPU）
- 每架无人机每秒发送5-10个MAVLink消息（HEARTBEAT + GLOBAL_POSITION_INT + ATTITUDE + SYS_STATUS + BATTERY_STATUS）
- 1000架 → 5000-10000 msg/s，接近单线程解析极限

### 2.5 持久化瓶颈

**TelemetryPersistenceService：**

```java
@Scheduled(fixedDelay = 5000)  // 5秒刷一次
@Transactional
public void flushBuffer() {
    while ((record = buffer.poll()) != null && count < 1000) { // 每次最多1000条
        ...
    }
    telemetryRepository.saveAll(telemetryList);  // JPA batch insert
    latestStateRepository.saveAll(latestStates); // upsert最新状态
}
```

**瓶颈分析：**
- 1000架 × 10Hz = 10000条/s，5秒累计50000条
- 但每次flush上限1000条 → 需要50次flush才能清空
- flush间隔5s → **永远清不完，buffer无限增长 → OOM**
- `saveAll()` 使用JPA逐条merge(非native batch insert)，效率低下
- TimescaleDB单实例写入能力约5000-20000 rows/s（取决于索引和chunk配置）

## 3. 网关层优化方案

### 3.1 网关多实例水平扩展

**当前架构：** 单实例网关处理所有无人机

**目标架构：** N个网关实例，每个实例负责一部分无人机

```
                        ┌──────────────────────┐
                        │   Nacos / Consul     │
                        │   服务注册与发现      │
                        └──────────┬───────────┘
                                   │ 注册/心跳
              ┌────────────────────┼────────────────────┐
              │                    │                    │
    ┌─────────▼──────┐  ┌─────────▼──────┐  ┌─────────▼──────┐
    │ Gateway Inst-0 │  │ Gateway Inst-1 │  │ Gateway Inst-2 │
    │ 负责: hash%3=0 │  │ 负责: hash%3=1 │  │ 负责: hash%3=2 │
    │ ~334架无人机    │  │ ~333架无人机    │  │ ~333架无人机    │
    └────────┬───────┘  └────────┬───────┘  └────────┬───────┘
             │                   │                   │
             └───────────────────┼───────────────────┘
                                 │
                      ┌──────────▼──────────┐
                      │  Kafka Cluster (3节点)│
                      │  telemetry.raw       │
                      │  commands.down       │
                      └──────────────────────┘
```

**分片策略（已有基础）：**

当前代码已有 `_owns_drone()` 方法：
```python
def _owns_drone(self, uav_id: str) -> bool:
    h = int(hashlib.md5(uav_id.encode()).hexdigest(), 16)
    return (h % self.total_instances) == self.instance_id
```

**优化方案：**

| 项目 | 当前 | 优化后 |
|------|------|--------|
| 实例数 | 1 | 3-5（根据规模动态） |
| 分片算法 | MD5 hash % N | 一致性哈希（ConsistentHash） |
| 注册发现 | 无 | Nacos/Consul服务注册 |
| 负载均衡 | 无 | 基于无人机数量的动态重均衡 |
| 命令路由 | 广播所有实例 | Kafka分区Key路由到正确实例 |

**一致性哈希优化理由：**
- 当前 `hash % N` 方案，增减实例时所有分片重排，导致大量无人机切换实例
- 一致性哈希环只影响相邻节点的1/N无人机重新分配
- 虚拟节点(vnode)保证负载均匀

**实现要点：**

```python
# 一致性哈希环（Gateway端）
class ConsistentHashRing:
    def __init__(self, nodes, virtual_nodes=150):
        self.ring = SortedDict()
        for node in nodes:
            for i in range(virtual_nodes):
                key = md5(f"{node}:{i}".encode()).hexdigest()
                self.ring[key] = node
    
    def get_node(self, uav_id: str) -> str:
        key = md5(uav_id.encode()).hexdigest()
        idx = self.ring.bisect_right(key) % len(self.ring)
        return self.ring.peekitem(idx)[1]
```

### 3.2 网关异步化重构

**DDS Gateway 异步化：**

| 组件 | 当前 | 优化后 |
|------|------|--------|
| 主循环 | `while True: sleep(0.05)` 同步轮询 | asyncio EventLoop |
| Kafka发送 | 同步构建 + async send | aiokafka AsyncProducer |
| ROS2 spin | 独立线程 | rclpy + asyncio bridge |
| 命令处理 | HTTPServer + ThreadPool | aiohttp / FastAPI |
| 心跳管理 | 每架无人机一个Thread | asyncio.Task (单线程千个) |

**MAVLink Gateway 异步化：**

```python
# 当前：阻塞式UDP接收
def _udp_loop(self):
    while self.running:
        data, addr = self._udp_socket.recvfrom(65535)  # 阻塞
        self._parse_mavlink_bytes(data, addr)           # 串行解析

# 优化后：asyncio UDP Protocol
class MavlinkProtocol(asyncio.DatagramProtocol):
    def datagram_received(self, data, addr):
        # 非阻塞接收，EventLoop调度
        asyncio.ensure_future(self._process(data, addr))
    
    async def _process(self, data, addr):
        messages = self._parse_mavlink_bytes(data, addr)
        for msg in messages:
            await self._dispatch(msg)  # 异步分发
```

**心跳线程合并（关键优化）：**

```
当前：1000架无人机 = 1000个心跳线程（offboard_heartbeat_loop）
优化后：1个asyncio任务管理所有心跳

async def heartbeat_manager(self):
    while self.running:
        now = time.time()
        tasks = []
        for uav_id, info in self._heartbeat_drones.items():
            if now - info.last_sent >= 0.25:  # 4Hz
                tasks.append(self._send_heartbeat(uav_id, info))
        if tasks:
            await asyncio.gather(*tasks)
        await asyncio.sleep(0.05)  # 20Hz检查周期
```

### 3.3 Kafka Producer优化

| 参数 | 当前值(默认) | 优化值 | 理由 |
|------|------------|--------|------|
| `linger.ms` | 0 (立即发送) | 5-10 | 攒批发送减少网络往返 |
| `batch.size` | 16384 (16KB) | 65536 (64KB) | 更大batch减少请求次数 |
| `buffer.memory` | 33554432 (32MB) | 67108864 (64MB) | 支持更多缓冲 |
| `compression.type` | none | lz4 | 减少网络带宽~60% |
| `acks` | 1 | 1 (保持) | 遥测数据可接受少量丢失 |
| `max.in.flight.requests` | 5 | 5 (保持) | 单连接并发请求数 |

**预期效果：**
- `linger.ms=5` + `batch.size=64KB`：多条消息合并为一次网络请求
- `compression.type=lz4`：遥测JSON重复字段多，压缩率约60%
- 1000架无人机 × 500B = 500KB/100ms，合并压缩后约200KB/100ms

## 4. Kafka 消息中间件优化方案

### 4.1 Kafka集群化

**当前：** 单Broker, KRaft模式, replication-factor=1

**目标：** 3-Broker集群, 完整ISR副本机制

```yaml
# docker-compose-kafka-cluster.yml (目标)
services:

      KAFKA_NUM_PARTITIONS: 32
      KAFKA_DEFAULT_REPLICATION_FACTOR: 3
      KAFKA_MIN_INSYNC_REPLICAS: 2
  kafka-2:
    environment:
      KAFKA_NODE_ID: 2
      ...
  kafka-3:
    environment:
      KAFKA_NODE_ID: 3
```

### 4.2 Topic分区策略优化

| Topic | 当前分区数 | 当前副本数 | 优化分区数 | 优化副本数 | 理由 |
|-------|----------|----------|----------|----------|------|
| telemetry.raw | 16 | 1 | 32 | 3 | 主数据流，需最大吞吐 |
| commands.down | 16 | 1 | 16 | 3 | 命令量较低，16分区足够 |
| commands.ack | 8 | 1 | 8 | 3 | 回执量低 |
| events.drone | 8 | 1 | 16 | 3 | 事件量随规模线性增长 |
| telemetry.aggregated (新增) | 16 | 3 | - | - | 聚合后的遥测数据 |
| drone.lifecycle (新增) | 8 | 3 | - | - | 无人机上下线事件 |

**分区数设计原则：**
- `telemetry.raw` 32分区：1000架无人机 / 32分区 ≈ 31架/分区
- 每个分区的消费吞吐约300 msg/s即可满足10 msg/s × 31架
- Consumer并行度 = 分区数，32个消费线程处理32个分区
- 分区数应大于等于最大Consumer实例数 × 每实例并行度

### 4.3 Consumer Group策略

**当前问题：**
```java
@KafkaListener(
    topics = "telemetry.raw",
    groupId = "ucs-telemetry-consumer",
    concurrency = "4"  // 单JVM 4线程
)
```

仅有4个消费线程处理16个分区，每个线程分配4个分区。

**优化方案：**

```
场景A: 单实例扩并行
  concurrency = 16 (每个线程1个分区)
  需要增加JVM线程池

场景B: 多实例扩展 (推荐)
  实例1: concurrency=8, 分配分区 0-7
  实例2: concurrency=8, 分配分区 8-15
  实例3: concurrency=8, 分配分区 16-23
  实例4: concurrency=8, 分配分区 24-31
  
  → 32个并行消费者，理论吞吐 32 × 500 msg/s = 16000 msg/s
```

### 4.4 消费端处理优化

**将串行处理拆解为并行流水线：**

```
当前（串行）：
  消费 → 反序列化 → Epoch校验 → Redis写 → DB写 → 分区路由 → WebSocket推送

优化后（流水线）：
  ┌─ Consumer线程 ─┐
  │ 消费 → 反序列化 │
  │ → Epoch校验     │
  │ → 写入Ring Buffer│
  └────────┬────────┘
           │ (Disruptor / BlockingQueue)
  ┌────────┼────────────────────────┐
  │        │                        │
  ▼        ▼                        ▼
 Redis    Persistence             WebSocket
 Pipeline  Batch Writer           Aggregator
 (批量)    (批量insert)           (按分区聚合后推送)
```

## 8. 前端优化方案

### 8.1 WebSocket推送优化

**当前问题：**
1. 全量推送：每次推送所有1000架无人机数据（500KB/次 × 10Hz = 5MB/s/客户端）
2. SimpleBroker：不支持多后端实例
3. 无数据压缩

**优化方案：**

**① 增量推送（Delta Compression）**

```typescript
// 后端：只推送变化的字段
interface TelemetryDelta {
  uavId: string;
  // 只包含变化的字段
  lat?: number;
  lon?: number;
  alt?: number;
  heading?: number;
  // 序列号用于检测丢失
  seq: number;
}

// 后端实现
public Map<String, Object> buildDelta(String uavId, Map<String, Object> current) {
    Map<String, Object> previous = lastSentState.get(uavId);
    if (previous == null) {
        lastSentState.put(uavId, current);
        return current;  // 首次：全量
    }
    Map<String, Object> delta = new LinkedHashMap<>();
    delta.put("uavId", uavId);
    delta.put("seq", seqCounter.incrementAndGet());
    for (var entry : current.entrySet()) {
        if (!entry.getValue().equals(previous.get(entry.getKey()))) {
            delta.put(entry.getKey(), entry.getValue());
        }
    }
    lastSentState.put(uavId, current);
    return delta;
}
```

**数据量对比：**

| 推送方式 | 数据量/次 | 频率 | 带宽/客户端 |
|---------|----------|------|-----------|
| 当前全量 | 500KB | 10Hz | 5 MB/s |
| 增量推送 | ~50KB(10%变化) | 10Hz | 500 KB/s |
| 增量+压缩 | ~20KB | 10Hz | 200 KB/s |

**② WebSocket Broker替换**

```
当前: SimpleBroker (内存)
  → 不支持多实例
  → 不支持消息持久化

方案A: RabbitMQ STOMP Broker (推荐)
  → 天然支持STOMP协议
  → 多实例后端共享一个RabbitMQ
  → 消息在Broker中自动扇出到所有订阅者

方案B: Redis Pub/Sub 作为中间层
  → 后端实例发布到Redis Channel
  → 每个实例订阅Channel并推送给本地WebSocket连接
  → 实现简单，但不如RabbitMQ可靠

方案C: 外部STOMP Broker (ActiveMQ)
  → Spring原生支持
  → 但引入额外组件
```

### 11.2 EpochManager 集群化

**当前问题：** `EpochManager` 使用 `ConcurrentHashMap` 存储在JVM堆中，多实例时各自维护独立的epoch映射，导致：
- 实例A认为px4_1 epoch=5，实例B认为epoch=3
- 实例B会错误地丢弃epoch=4的有效消息

**解决方案：Redis原子Epoch**

```java
@Component
public class RedisEpochManager {
    private final StringRedisTemplate redis;
    private static final String EPOCH_PREFIX = "epoch:";
    
    public boolean validateEpoch(String uavId, long msgEpoch) {
        String key = EPOCH_PREFIX + uavId;
        // Lua脚本：原子比较并更新
        String script = """
            local current = tonumber(redis.call('GET', KEYS[1]) or '0')
            if tonumber(ARGV[1]) >= current then
                redis.call('SET', KEYS[1], ARGV[1])
                redis.call('EXPIRE', KEYS[1], 86400)
                return 1
            end
            return 0
        """;
        Long result = redis.execute(
            new DefaultRedisScript<>(script, Long.class),
            List.of(key), String.valueOf(msgEpoch)
        );
        return result != null && result == 1;
    }
    
    public long getCurrentEpoch(String uavId) {
        String val = redis.opsForValue().get(EPOCH_PREFIX + uavId);
        return val != null ? Long.parseLong(val) : 0L;
    }
}
```

| redis.used.memory.pct | >80% | 内存告警 |
| redis.connected.clients | >500 | 连接过多 |
| redis.keyspace.misses.ratio | >50% | 缓存效率低 |
| redis.slowlog.count | >10/min | 慢查询 |

**DB级：**

| 指标 | 告警阈值 | 说明 |
|------|---------|------|
| pg.active.connections | >80% pool | 连接池接近耗尽 |
| pg.query.duration.p99 | >100ms | 慢查询 |
| pg.deadlocks | >0 | 死锁 |
| pg.replication.lag | >1s | 主从延迟 |

### 12.3 分布式链路追踪

**方案：Spring Cloud Sleuth + Zipkin/Jaeger**

```yaml
spring:
  sleuth:
    sampler:
      probability: 0.1  # 10%采样率（生产环境）
    messaging:
      kafka:
        enabled: true    # Kafka消息自动注入trace
  zipkin:
    base-url: http://jaeger:9411
```

每条请求生成唯一 `traceId`，贯穿 Gateway → Kafka → Consumer → DB → WebSocket 全链路。

## 13. 性能测试指标体系

### 13.1 测试维度

| 维度 | 测试内容 | 工具 |
|------|---------|------|
| **吞吐量(QPS/TPS)** | 各层最大处理能力 | JMeter, wrk, kafka-perf-test |

| **资源(Resource)** | CPU/Mem/IO/Net | Prometheus + Grafana |
| **容错(Fault Tolerance)** | 组件故障后表现 | Chaos Engineering |

### 13.2 性能测试用例

**测试用例1：遥测吞吐量基准**
```
场景: N架虚拟无人机 × 10Hz遥测
指标: 
  - Gateway→Kafka 产出率 (msg/s)
  - Kafka→Consumer 消费率 (msg/s)
  - Consumer→Redis 写入率 (ops/s)
  - Consumer→DB 持久化率 (rows/s)
  - Consumer→WebSocket 推送率 (msg/s)
  - 端到端延迟 P50/P95/P99

阶梯负载:
  Step 1: 10架 → 100 msg/s (当前上限，验证基线)
  Step 2: 50架 → 500 msg/s
  Step 3: 100架 → 1000 msg/s
  Step 4: 200架 → 2000 msg/s
  Step 5: 500架 → 5000 msg/s
  Step 6: 1000架 → 10000 msg/s
  Step 7: 2000架 → 20000 msg/s (目标上限的2倍)

通过标准:
  - 10000 msg/s 时 Consumer Lag < 100
  - 端到端延迟 P99 < 200ms
  - CPU使用率 < 80%
  - 无OOM、无GC暂停 > 100ms
```

**测试用例2：命令响应延迟**
```
场景: 同时向N架无人机发送TAKEOFF命令
指标:
  - 命令发送延迟 (API→Kafka)
  - 命令处理延迟 (Kafka→Gateway→PX4)
  - ACK回传延迟 (PX4→Gateway→Kafka→WebSocket)
  - 端到端命令延迟 (API请求→前端收到ACK)

阶梯负载:
  Step 1: 10架同时起飞
  Step 2: 50架同时起飞
  Step 3: 100架同时起飞
  Step 4: 500架分批起飞(100/批)
  Step 5: 1000架分批起飞

通过标准:
  - 100架同时命令，端到端延迟 P99 < 500ms
  - 命令丢失率 0%
  - ACK回传率 100%
```

**测试用例3：WebSocket推送吞吐**
```
场景: N个前端客户端同时连接，接收遥测推送
指标:
  - 单客户端接收带宽 (KB/s)
  - 推送延迟 (遥测产生→前端渲染)
  - 服务器WebSocket连接数
  - 服务器出带宽

阶梯负载:
  Step 1: 5客户端 × 100架无人机
  Step 2: 10客户端 × 500架无人机
  Step 3: 20客户端 × 1000架无人机
  Step 4: 50客户端 × 1000架无人机

通过标准:
  - 20客户端×1000架，推送延迟P99 < 200ms
  - 单客户端带宽 < 1MB/s（增量推送）
  - 服务器出带宽 < 100MB/s
```

**测试用例4：组件故障容错**
```
场景: 各组件单点故障
测试项:
  4.1 杀掉1个Kafka Broker → 验证生产/消费不中断
  4.2 杀掉1个Redis Master → 验证自动主从切换
  4.3 杀掉1个后端实例 → 验证其他实例接管消费
  4.4 网关实例重启 → 验证无人机自动重新分配
  4.5 数据库主从切换 → 验证写入不中断

通过标准:
  - 单组件故障时服务可用性 > 99%
  - 故障恢复时间 < 30s
  - 故障期间无数据丢失（命令类）
  - 故障期间遥测丢失 < 5s数据量
```

**测试用例5：长时间稳定性**
```
场景: 1000架无人机持续运行72小时
指标:
  - 内存泄漏: 各服务RSS增长趋势
  - GC行为: Full GC频率, 暂停时间
  - Kafka: 磁盘增长, Log Compaction效果
  - DB: 连接池泄漏, 慢查询趋势
  - WebSocket: 连接断开/重连次数

通过标准:
  - 72h内无服务OOM
  - 72h内无GC暂停 > 200ms
  - Kafka磁盘增长线性可预测
  - DB连接池使用率稳定
```
